# 视频转白模：AI 视频参考视频实现机制与当前项目适配调研

> **目的**：解释 AI 视频制作语境中“视频转白模”通常指什么，拆解“输入视频 → 白灰参考视频”的真实实现路径，并判断它与当前项目预演台白膜导出的关系。
>
> **状态**：研究草稿。结论来自当前仓库源码、已有预演台/云端 Agent 文档、外部产品资料和论文/项目资料；没有把外部产品的宣传能力当作当前项目已经实现的事实。
>
> **证据范围**：当前项目 `web/src/components/canvas/previs/`、`web/src/lib/canvas/previs/`、媒体转换节点、视频生成 Provider、`backend/internal/app/` 的任务与协议代码，以及[预演台系统深度调研报告](previs-workbench-deep-research.md)、[预演台与云端 Agent 依赖、执行机制和资源占用调研](previs-agent-dependency-resource-research.md)、[云端 Agent 深度调研报告](cloud-agent-deep-research.md)。外部资料列在[外部资料与证据](#外部资料与证据)中。

本文统一使用行业中更常见的“白模”一词。当前项目预演台的文件名、UI 文案或历史说明中可能写作“白膜”；这里的用词差异不表示两条不同的技术路线。

## TL;DR

在 AI 视频制作中，“视频转白模”最常见的产品含义是：把一段已有视频转成颜色和纹理被简化的白灰色参考视频，同时尽量保留动作、人物走位、镜头运动、节奏和空间关系；再把这段视频作为后续视频生成的运动或构图参考。它通常输出的是视频，不是可编辑的 3D 模型文件。

实现上至少要区分三类能力：

1. **视频级白模参考**：在不向用户交付可编辑 3D 场景的前提下，从视频中提取人物/主体、关键帧、姿态、深度、分割、光流或相机提示，再生成关键帧白模图、深度参考视频或白灰参考视频。实现可以是关键帧抠图与合成、2D/2.5D 代理处理或受控制的视频生成；这类产品路径本身不要求建立可编辑的三维网格。
2. **视频到 3D 场景重建**：从输入视频估计人物/道具/相机/深度和时间轨道，拟合到可编辑的 3D 对象、骨骼和相机，再用 Blender、Three.js 或其他渲染器输出白模图片/视频。这个结果才可能继续被编辑、重新打光或渲染成多个版本。
3. **已有结构化场景的白膜渲染**：输入已经是 `PrevisScene`，系统只负责把材质、灯光和渲染模式切到白膜。这是当前项目已经实现的路径，但它不是“任意输入视频自动转成白模”。

当前项目已经实现了第三类能力中“从结构化场景到白膜视频”的渲染/物化路径：已有结构化 `PrevisScene`，浏览器 Three.js 可以把它录制成白膜 MP4，并把视频作为 `reference_video` 节点回写画布。当前没有发现第一类“任意输入视频 -> 白模参考视频”任务，也没有发现第二类“输入视频 -> 自动生成 `PrevisScene`”的完整重建流水线。

因此，新功能的合理第一阶段不是把预演台改造成视频重建器，而是增加一个独立的、可取消可重试的“白模参考视频任务”，复用现有资源、任务、参考视频和画布回写合同。

一组 2026 年 9 月发布的 LibTV 使用教程提供了一个具体的产品案例：用户从参考视频进入“逐帧拉片”相关操作，并可在其下拉菜单中选择“深度动作捕捉”；两者配合后得到关键帧/音频等拆解素材和深度/白模参考视频，再把角色参考图、场景参考图、音频和深度视频连接到后续视频生成节点。[LibTV 深度动捕案例教程](https://www.10100.com/article/152252915) [LibTV 深度动捕实测与逐帧拉片说明](https://www.10100.com/article/150012804) 这些文章属于第三方体验，不是 LibTV 内部技术规格；其相互印证能支持用户工作流方向，但不能直接证明任务 API、内部模型或可编辑 3D 交付。文章把结果描述成“带深度的空间骨架”或由胶囊体、方块和简单几何体组成的白模画面，并强调它承载人物位置、运动轨迹和机位运动轨迹；但公开材料没有展示可下载的 Blender 场景、网格、骨骼或相机工程文件。因此，这个案例应归入“视频级白模参考”路线：内部可能使用 3D 代理几何或其他中间表示，但不能据此断言向用户交付了可编辑的 3D 场景，也不能直接归类为完整的“视频到 3D 场景重建”。更完整的外部产品证据和边界见 [LibTV「逐帧拉片」产品分析与证据档案](libtv-shot-breakdown-product-analysis.md)。

## 0. 先用人话回答：一个白模视频到底从哪里来

“白模视频”不是一个所有平台都内置、点击一次就能稳定得到的标准文件。它通常来自下面三类来源：

1. **已有 3D 场景或预演场景的白膜渲染**。人物、道具和相机已经被建成结构化场景，渲染器只把材质换成浅灰或低纹理。这是当前项目已经能做的路径，但输入必须先是 `PrevisScene`，不能直接把任意真人视频交给预演台自动还原。
2. **在线视频到视频服务**。用户上传普通视频，服务在后台做视频分析和生成/重绘，最后返回一段 MP4。它最接近“上传视频，得到白模参考视频”的产品体验，但网页上能操作不等于有正式 API，是否允许自动化调用、是否支持下载、时长和价格限制都要逐项核实。
3. **自建开源流水线**。以 Wan2.1 VACE、ComfyUI 工作流或其他视频控制组件为基础，自己准备模型权重、GPU、预处理节点、队列和转码服务。这类方案确实可以产出视频文件，但不是安装一个工具后就自动完成“视频转白模”；白模外观、控制信号、跨帧一致性和生产运维都要自行组装。

因此，回答“有没有现成的白模视频”时，必须把三个问题分开：

- **网页上能不能点出来**：可能可以，取决于具体产品和账号权限；
- **有没有正式 API 可以集成**：需要看官方 API、SDK、授权、配额和服务条款，不能从网页按钮推断；
- **有没有开源代码可以自部署**：有视频到视频和可控生成组件，但通常需要自行拼装成完整任务服务。

| 方案 | 输入与输出 | 是否通常能拿到 MP4 | 是否可直接集成 | 服务器主要负担 | 适合当前项目的用途 |
| --- | --- | ---: | --- | --- | --- |
| 当前项目预演台 | 结构化 `PrevisScene` -> 浏览器录制的白膜视频 | 是 | 已有内部路径 | 主要是资源上传、保存和任务记录；渲染主要发生在浏览器 | 先做可控的镜头预演和参考视频 |
| 专门的在线白模/视频重绘服务 | 普通视频 -> 白灰或 clay-like 视频 | 通常可以 | 只有在有正式 API 时才可 | 文件上传、结果下载、任务状态和资源存储 | 先验证产品价值和画面质量 |
| 通用视频到视频 API | 普通视频 + 提示词/控制信号 -> 输出视频 | 取决于供应商 | 有正式 API 时最适合 MVP | 任务代理、轮询/回调、结果物化和计费 | 第一版优先候选 |
| ComfyUI + Wan VACE 等自部署组件 | 视频、参考图、深度/姿态控制视频 -> 输出视频 | 是 | 需要自行封装 HTTP/队列适配层 | GPU 推理、显存调度、模型权重、转码和清理 | 做原型或自有 GPU 场景 |
| 完整视频到 3D/预演重建 | 普通视频 -> 候选演员、相机、道具和轨道 -> 白膜视频 | 可以 | 需要自研或组合多个视觉模型 | 分析、拟合、修正、场景持久化和人工确认 | 第二阶段，不适合先做 MVP |

公开产品可以作为“先试效果”的入口，但不能直接当成集成结论：Kavilo 的页面明确把产品定位为“视频转白模参考视频”，并给出上传视频、生成白模、再把结果送入后续视频生成的完整体验；Krea、Higgsfield 等通用 video-to-video/视频重绘产品则更偏向风格迁移，可能尝试生成 clay-like 外观，但不等于它们已经提供了面向白模参考的专用模式。网页产品是否有正式 API、能否批量调用、是否允许在当前项目中保存和转发结果，仍需查看各自的官方开发者文档和服务条款。[Kavilo：视频转白模工具](https://www.kavilocreativeai.app/zh/video-to-3d-white-model)、[Krea Video Restyle](https://www.krea.ai/video-restyle)、[Higgsfield Video to Video](https://higgsfield.ai/video-to-video)

如果目标是“尽快在当前项目里验证白模参考视频是否有用”，最现实的顺序是：先选择一个有正式 API 的视频到视频能力，输出独立的 `reference_video` 资源；如果暂时只有网页服务，就把它当人工实验工具，先验证画面质量，不要把网页自动化当成生产集成方案；如果必须自部署，再用 ComfyUI/Wan VACE 一类工作流验证模型效果，随后再为它包一层受控 Worker。

### 0.1 LibTV 案例中的两个中间产物

外部产品行为的证据索引、官方前端文案核对和字段级未知项，另见 [LibTV「逐帧拉片」产品分析与证据档案](libtv-shot-breakdown-product-analysis.md)。本节只保留与“视频转白模”实现直接相关的结论。

这些文章把“逐帧拉片”和“深度动作捕捉”放在同一条工作流中，但它们解决的问题不同：

| 功能 | 输入 | 产物 | 用途 | 是否等于 3D 建模 |
| --- | --- | --- | --- | --- |
| 逐帧拉片 | 原始视频 | 关键画面、动作节奏、原始音频等结构化素材 | 了解镜头、角色数量、关键构图，并准备角色/场景替换素材 | 否 |
| 深度动作捕捉 | 原始视频或裁剪后的动作片段 | 深度/白模参考视频，画面中只保留动作、走位、空间关系和机位信息 | 作为后续参考生视频的动作和构图控制输入 | 公开材料未展示可编辑 3D 场景交付；画面可能使用 3D 代理几何 |

从文章可以确认的产品级流程是：

```text
原始动作视频
  -> 画布内裁剪（可选）
  -> 逐帧拉片：关键帧图片 + 音频 + 结构化素材
  -> 深度动作捕捉：深度/白模参考视频
  -> 角色图片 + 场景图片 + 音频 + 提示词
  -> 参考生视频
  -> 最终成片或智能剪辑
```

因此，LibTV 这条路径应按“关键帧/深度参考驱动的视频级参考工作流”记录，而不是直接按“本地 Agent 调 Blender 的 3D 重建工作流”记录。它可以通过视频分析、关键帧提取、人物/主体分割、深度图、3D 代理几何或白模参考图生成来实现；这些实现可以不向用户交付可编辑的三维网格。对多人动作而言，深度参考视频还承担人数、站位、前后关系、队形和角色绑定；如果只记录一条整体光流，通常无法表达“哪个角色对应哪张参考图”。

文章没有公开 LibTV 的模型和内部算法，所以不能从外部教程确定它是“纯抠图”、深度图重绘、简单 3D 代理渲染还是其他视频处理方式。但这不影响产品层面的判断：它输出的是供后续视频生成使用的关键帧/深度参考素材；公开流程没有证明用户可以把结果作为 Blender 场景继续编辑。

这篇文章还展示了一个值得写入生成合同的提示词规则：白模视频应作为时间线、镜头构图和动作顺序的高优先级基准，角色参考图只负责外观和身份，提示词负责环境、材质和特效等白模没有表达的内容。这个规则比简单写一句“参考白模动作”更可执行。

但证据强度需要单独标注：该页面是第三方产品教程和体验文章，页面本身声明内容来源于网络；它可以用来说明一种真实产品工作流和用户可见的交互方式，不能用来证明 LibTV 的内部模型、接口、可复现成功率，也不能证明当前项目已经具备同样的深度动作捕捉能力。

### 0.2 两个功能是产品上的连续步骤，还是一个后端复合任务

从用户操作层看，两者存在明确的前置/后置关系：文章展示的是在参考视频的“逐帧拉片”下拉菜单中选择“深度动作捕捉”，而不是在一个与视频拆解完全无关的 3D 建模页面中启动它。这足以支持下面的产品级描述：

```text
参考视频
  -> 逐帧拉片相关的拆解/准备
  -> 深度动作捕捉
  -> 深度/白模参考素材
```

但不能把这个 UI 关系直接升级为后端实现事实。两篇公开文章在叙述具体案例时对“先深度动捕还是先逐帧拉片”的文字顺序并不完全一致：一篇强调从“逐帧拉片”入口选择“深度动作捕捉”，另一篇把两者列为连续的解决步骤。因此当前最稳妥的结论是：

- **已能确认**：在 LibTV 的用户工作流中，两者是连续配合的功能；逐帧拉片提供关键帧、动作节奏、音频等素材，深度动作捕捉提供深度/白模参考素材。
- **尚不能确认**：选择深度动作捕捉时，后端是否一定创建一个内部的逐帧拉片子任务；两者是否共享同一个任务 ID、缓存分析结果或由一个复合任务一次性完成。

如果当前项目实现类似能力，应把“逐帧拉片分析结果”作为深度动作捕捉可依赖、可复用的中间产物，并以源视频哈希、裁剪区间和分析版本做缓存键。这样既能表达产品上的连续流程，也不会把同一段视频重复分析；是否在 UI 上显示为一个按钮、两个阶段还是一个可恢复的复合任务，属于后端任务编排选择，不能由外部页面名称推断。

### 0.3 “逐帧拉片”大概率不是逐帧导出 JPG

公开截图给出了一个比文章文字更有用的线索：LibTV 的“逐帧拉片”节点在执行前提供“分镜”“动态”“音乐”三个产出方向，用户点击“开始拉片”后才开始处理视频。[LibTV 深度动捕实测与逐帧拉片说明](https://www.10100.com/article/150012804) 结合文章对“关键画面、动作节奏及音频”“结构化素材”的描述，更合理的理解是：它是一个**按镜头和时间组织的复合分析/素材物化任务**，而不是把视频的每一帧都保存成一张图片。

从产品结果倒推，三类输出大致对应：

| 产品产出 | 公开材料能确认的内容 | 较稳妥的工程解释 | 不能直接断言的内容 |
| --- | --- | --- | --- |
| 分镜 | 关键画面、镜头/构图等可继续创作的素材 | 镜头切分 + 代表帧选择 + 镜头级视觉描述/提示词 + 时间戳 | 具体采用何种切镜算法、是否由同一个 VLM 生成全部描述 |
| 动态 | 动作节奏、人物动作、运镜或空间关系等动态信息 | 运动特征提取、主体/人物跟踪、镜头运动估计，必要时再由模型总结成结构化字段 | 是否直接生成深度视频；公开流程把深度动作捕捉作为相邻的另一项能力 |
| 音乐 | 原始音频可被取出并接到后续生成节点 | 音轨拆出/转码，并可附加 ASR 时间戳、节拍或能量曲线 | “音乐”是否包含完整节拍分析、歌词识别或只代表原始音频资源 |

这里的“逐帧”应理解为“细粒度地逐镜头拆解”，而不是“每一帧都成为一个业务节点”。如果一个 10 秒视频按 24 或 30 fps 全量导出，结果会产生数百个图片对象；公开案例反而强调关键画面、结构化素材和后续节点复用，因此产品更可能采用“切镜 + 自适应采样 + 代表帧筛选”的方式，只把少量高价值帧物化为图片，把完整音轨单独保存，把分析结果保存为 JSON/卡片。

一个不依赖 LibTV 内部实现细节、但能解释这些公开行为的参考流水线是：

```text
源视频
  -> 容器/时长/帧率/音轨探测
  -> 低分辨率代理与统一时间轴
  -> 镜头边界检测
       ├─ 硬切、淡入淡出、闪白候选
       └─ 长镜头内的内容变化与运动强度
  -> 自适应取样与代表帧筛选
       ├─ 镜头首帧/尾帧
       ├─ 构图或主体显著变化帧
       ├─ 动作峰值/关键姿态帧
       └─ 清晰度、重复帧和遮挡过滤
  -> 视觉分析
       ├─ 景别/视点/构图
       ├─ 人物与主体数量、位置和身份线索
       ├─ 动作、情绪、道具和场景
       └─ 运镜/镜头节奏候选
  -> 音频分析
       ├─ 原始音轨物化
       ├─ 语音转写与时间戳（有对白时）
       └─ 节拍/能量/静音区间（有音乐时，可选）
  -> VLM/LLM 将逐镜头证据整理为结构化卡片
  -> 图片、音频、JSON 和画布节点/连线物化
```

其中“镜头边界、帧时间、音轨时长、清晰度、光流和人体关键点”适合由确定性工具或专用视觉模型先计算；“这是什么景别、角色正在做什么、这段镜头的叙事作用是什么”再交给视觉语言模型总结。直接把整段视频交给一个模型要求它同时给出精确时间点、镜头边界和创作提示，成本更高，也更难复现。

更具体地说，代表帧选择可以采用以下组合，而不是固定每 N 帧取一张：

1. 先按镜头边界切成 `shotSegment`，为每个镜头保留首帧、尾帧和少量均匀采样帧。
2. 在长镜头内计算相邻帧的颜色/结构差异、光流强度或视觉 embedding 距离，补充构图变化和动作峰值帧。
3. 用清晰度、主体可见面积、多人遮挡和帧间相似度做过滤，避免把运动模糊、重复画面和过渡帧当作关键帧。
4. 把最终图片数量限制在模型输入和用户可管理的范围内；完整视频仍保留为原始参考，不让关键帧集合冒充整段视频。

“动态”也应拆成两个层次：一层是可计算的运动证据，例如人物框/关键点轨迹、全局光流、镜头平移或旋转候选；另一层是面向创作的语言摘要，例如“人物从画面左侧走到中央，镜头跟拍后轻微推进”。前者可以复核和重算，后者适合直接进入提示词，但不能只保存后者，否则用户无法判断模型为什么得出这个结论。

### 0.4 当前项目已经具备哪些可复用积木

当前仓库有几块与这条推测流水线相邻的能力，但它们还没有组成“逐帧拉片”主链：

- [`canvas-video-frame.ts`](../../web/src/lib/canvas/canvas-video-frame.ts) 可以在浏览器加载视频、按指定时间 seek、抽取 PNG，并报告单帧失败；它是“用户手工选择时间点取帧”的基础，不是自动切镜和关键帧算法。
- [`canvas-video-frame-dialog.tsx`](../../web/src/components/canvas/canvas-video-frame-dialog.tsx) 提供首帧、尾帧和当前画面提取，提取后只创建图片节点，不自动发起生成任务；这与“逐帧拉片”需要的批量分析和镜头级卡片仍有明显差距。
- [`task_timeline.go`](../../backend/internal/app/task_timeline.go) 的时间线转写任务会读取资源，用本地 `ffmpeg` 预处理音频，再调用 `whisper.cpp`，把带时间戳的 segments 和 SRT 保存到持久化任务结果；这可以复用为“音乐/对白”输出的一部分，但它不做镜头分析或关键帧选择。
- [`transcription_whisper.go`](../../backend/internal/app/transcription_whisper.go) 只负责 whisper.cpp HTTP 客户端和时间戳结果解码，不能据此推断仓库已有通用的视频内容理解服务。
- Agent 当前支持明确的首帧/尾帧节点语义和 `reference_video` 协议角色；它能表达“把哪张图作为首帧/尾帧”，但没有发现自动产生 `ShotAnalysisResult` 或批量镜头卡片的业务主链。

因此，如果在当前项目实现“逐帧拉片”，建议新增独立的分析任务，而不是把逻辑塞进现有的视频生成或图片转换节点。最小中间产物可以是：

```text
ShotAnalysisResult
- sourceAssetId / sourceVideoHash
- sourceDurationMs / fps / width / height
- analysisVersion
- shots[]
  - shotId / startMs / endMs / durationMs
  - keyframeAssetIds[]
  - shotSize / viewpoint / cameraMotion
  - subjects[] / actionSummary / sceneSummary
  - transcriptSegmentRefs[] / audioAssetId
  - confidence / warnings[]
- audioAssetId
- transcriptRef
- analysisArtifacts[]
```

`ShotAnalysisResult` 是建议的数据模型，不是当前项目已经存在的类型。画布只应保存结果资源和摘要引用；大规模帧特征、光流、姿态序列和模型原始响应应放在版本化资源或任务存储中，不要把整段分析原文塞进画布 JSON。

无论选择哪条路线，都不要把以下三件事混为一谈：

- **灰度滤镜**只是改颜色，不能把原视频中的服装、脸和纹理从生成条件中真正去掉；
- **在提示词里写“白模”**不能保证动作、相机和外观都稳定，通常仍需要姿态、深度、分割或相机等控制信号；
- **白模参考视频**不是可编辑的 Blender/Maya 网格。只有视频分析后重新拟合场景，才可能得到 `PrevisScene` 候选，而且仍需要人工校正。

一个外部服务或自建 Worker 实际上都要经历同一条任务链：

```text
上传源视频并物化资源
  -> 创建持久化转换任务
  -> 解码、规范化和镜头切分
  -> 提取姿态 / 深度 / 分割 / 相机等控制信号（可选）
  -> 视频到视频生成或 3D/预演重新渲染
  -> 跨帧一致性和 MP4 完整性检查
  -> 保存输出资源并建立派生关系
  -> 作为 reference_video 提供给后续视频生成
```

这也是为什么“获取一个白模视频”不能设计成一次同步 HTTP 请求。浏览器只负责上传、查看进度和播放结果；任务事实、重试、取消、结果校验和超时恢复必须由后端与 Worker/上游服务共同承担。当前项目已有“上游实际可以成功，但前端固定等待时间先报超时”的用户反馈，因此白模任务不能复用这种以客户端等待上限推断最终失败的语义。

## 1. 先统一术语：三个相近但不同的能力

### 1.1 白膜渲染：已有 3D 场景的材质/渲染模式

白膜渲染的输入已经是结构化场景：人物、道具、相机、灯光和关键帧都存在。系统只是把颜色、纹理和材质简化，再输出一张图或一段视频。

```text
PrevisScene
  -> Three.js / Blender / 其他 3D 渲染器
  -> clay / white-material override
  -> 白膜视频
```

这条路径不能回答“输入视频中人物怎么走、相机怎么动”。它只回答“已经搭好的场景如何以白膜形式输出”。

### 1.2 视频转白模：面向 AI 视频生成的参考视频转换

在产品语境中，“白模”通常是参考视频的外观和信息密度，而不是一个工程文件格式。输入可以是真人视频、动画视频或已经存在的 3D 白模视频；输出是更中性的白灰视频，用于把运动、构图和节奏与角色外观、材质风格解耦。

```text
原始视频
  -> 视频分析或视频到视频转换
  -> 白灰 / clay-like 参考视频
  -> AI 视频生成模型
```

外部产品资料通常把这类结果称为“白模参考视频”，并明确区分“参考视频”和“可编辑 3D 模型文件”。例如，Kavilo 的产品说明将动作、运镜和场景结构列为保留目标，同时声明输出不是摄影测量或 3D 扫描得到的可编辑网格。[Kavilo：视频转白模工具](https://www.kavilocreativeai.app/zh/video-to-3d-white-model)

阿里云 Wan 3.0 视频生成文档把 `Motion reference` 和 `Clay render reference/render` 作为不同的参考模式描述，也说明白模参考的价值在于提供运动、构图或渲染控制；这不应被解读为每次都会生成 3D 场景文件。[Wan 3.0 视频生成提示词指南](https://help.aliyun.com/en/model-studio/wan3-video-generation-prompt-guide)

### 1.3 视频到可编辑 3D 白模：计算机视觉重建

这是一条更重的能力：系统要从视频估计人物、相机、深度、地面、道具和时间关系，再映射到可编辑的 3D 对象和轨道。

```text
视频
  -> 人物/物体跟踪
  -> 2D/3D 姿态
  -> 相机和深度
  -> 场景几何与时间平滑
  -> 结构化 PrevisScene
  -> 白膜渲染
```

它的交付物才可能包含演员、相机和关键帧，但它不等于行业里所有“视频转白模”产品都做了 3D 重建。

### 1.4 “白模参考视频”和“3D 白模场景”的判定规则

研究或选型时，不要根据画面看起来像胶囊体、方块或灰色模型，就断言系统已经完成 3D 建模。应根据交付物和可操作性判断：

| 观察到的结果 | 更准确的能力分类 | 是否能继续在 Blender/预演台中编辑 |
| --- | --- | --- |
| 只有一段灰模 MP4，可连接到后续视频生成 | 视频级白模参考 | 不能据此判断；通常不能直接编辑 |
| 能导出人物网格、骨骼、相机和关键帧 | 视频到 3D 场景重建 | 可以，但还要检查格式、绑定和坐标是否可用 |
| 能在当前项目预演台里移动人物、改机位、改时间轨道并重新渲染 | 结构化预演场景 | 可以；当前项目的 `PrevisScene` 属于这一类 |

“关键帧抠图”是视频级白模的一种实现候选；“本地 Agent 调 Blender”是 3D 重建或场景重建的一种执行方式。二者不是互斥的：本地 Agent 也可以只调用分割、姿态和视频合成工具，不启动 Blender；反过来，3D 重建也可以由固定 Worker 或脚本执行，不一定需要 Agent。设计系统时应先冻结输出合同，再决定内部是否使用 Agent、Blender 或视频生成模型。

## 2. 行业实现的核心拆分

一段白灰视频要成为可用的 AI 视频参考，系统需要同时满足两个目标：

- **结构保持**：动作、走位、镜头方向、镜头速度、时长和主体关系不能严重漂移。
- **外观去耦**：原视频中的身份、服装、纹理、颜色、品牌和复杂光照不能继续主导最终生成。

这两个目标往往由不同模块负责。控制信号负责结构，扩散模型或渲染器负责外观。ControlNet 论文展示了将边缘、深度、姿态等空间条件注入扩散模型的通用方式；视频版本则要再处理跨帧一致性。[ControlNet](https://arxiv.org/abs/2302.05543)、[Control-A-Video](https://arxiv.org/abs/2305.13077)

可以抽象成：

```text
source video
  -> canonical media
  -> control extraction
       ├─ pose / skeleton
       ├─ depth / normal
       ├─ segmentation / subject mask
       ├─ optical flow / motion trajectory
       ├─ camera trajectory
       └─ shot boundaries
  -> white-model target definition
  -> video generation or 3D re-render
  -> temporal consistency pass
  -> validation and asset materialization
```

“视频转白模”不是单个模型按钮，而是一个由媒体处理、视觉分析、生成/渲染、质量控制和资源管理组成的任务。

## 3. 路线 A：视频到视频白模化

这是当前最接近“输入视频 → 输出白模参考视频”的实现。

### 3.1 输入规范化

任务先把输入视频转换成模型可控的规范形式：

- 解码容器，确认视频轨和音频轨是否存在；
- 统一帧率、分辨率、方向和色彩空间；
- 读取真实时长，拒绝无法解析或只有首帧的文件；
- 检测镜头切换，避免把两个镜头当成同一个连续运动；
- 按最大时长和文件大小限制切片；
- 生成低分辨率代理视频供分析，保留原视频用于最终对齐。

这一步不应依赖浏览器把大视频转成 data URL 再塞进 JSON。视频应先物化到受控资源存储，任务只保存 `assetId`、哈希、时长和规格。

### 3.2 从视频提取控制信号

不同产品会选择不同的控制强度。常见信号如下：

| 信号 | 作用 | 白模化任务中的价值 | 典型风险 |
| --- | --- | --- | --- |
| 2D 姿态 | 保留人体关节运动 | 让 AI 复用动作 | 遮挡时关节跳变 |
| 3D 姿态/人体参数 | 保留空间姿态和朝向 | 减少前后景漂移 | 单目深度和尺度不确定 |
| 深度 | 保留前后景层次和遮挡 | 让镜头空间关系更稳定 | 远处和反光物体误差大 |
| 法线/边缘/线稿 | 保留轮廓和几何结构 | 适合低纹理白模 | 细节过多会把原外观带回去 |
| 分割/跟踪 | 区分人物、道具、背景 | 允许分别控制外观 | 多人身份交换 |
| 光流/运动轨迹 | 保留局部运动 | 辅助时间一致性 | 快速运动、运动模糊不稳定 |
| 相机轨迹 | 保留推拉摇移、旋转和视角 | 复用镜头语言 | 单目视频存在尺度和内参歧义 |
| 镜头切分 | 保护镜头边界 | 防止跨镜头污染 | 硬切、闪白、特效容易误判 |

姿态、深度和边缘可以作为逐帧控制图；相机轨迹和光流更适合成为时间条件或一致性约束。MotionCtrl 研究把相机运动和主体运动作为可控制的条件，CameraCtrl 则专门讨论相机轨迹对文本到视频生成的控制；这些工作说明“动作控制”和“相机控制”最好在接口和模型条件中分开，而不是都塞进一段提示词。[MotionCtrl](https://arxiv.org/abs/2312.03641)、[CameraCtrl](https://arxiv.org/abs/2404.02174)

### 3.3 定义“白模”目标

白模不是一个固定的颜色值。任务需要先确定输出风格：

- **材质白模**：保留人物和场景轮廓，统一成浅灰、低饱和、粗糙材质；
- **线框/姿态白模**：突出骨架、轮廓和运动路径，牺牲表面完整度；
- **块面预演**：把人物、建筑和道具简化为几何块，重点表现比例和机位；
- **低细节灰模**：保留一定的明暗和空间层次，方便视频模型识别主体关系。

目标定义至少应固定：

```text
palette / roughness / contrast
background treatment
actor detail level
prop detail level
camera and lens preservation
motion preservation strength
source appearance suppression strength
```

只在提示词中写“白模、白灰、clay”是不够的。模型可能保留原人物脸、衣服颜色或纹理，也可能生成闪烁的灰白真人视频。生产实现需要把目标风格作为模型参数、参考图、控制图、后处理或渲染材质共同约束。

### 3.4 两种视频生成方式

#### 方式 A：直接视频到视频扩散

```text
输入视频帧 / latent
  + 姿态、深度、边缘、分割等条件
  + 白模提示词和负向约束
  -> 时空扩散模型
  -> 白模视频
```

典型机制是把源视频编码成逐帧 latent，在去噪过程中加入空间控制分支和时间注意力；模型以“白模”目标重新生成每帧，而不是简单把 RGB 像素转成灰度。

优点：

- 可以在不建立完整 3D 场景的情况下工作；
- 可以同时改变人物身份、服装和环境；
- 可以直接适配已有视频到视频模型或带参考视频的模型。

缺点：

- 输出仍可能是风格转换结果，不是几何正确的 3D 白模；
- 容易出现闪烁、身份泄漏、局部漂移、脚底滑动和相机抖动；
- 生成结果的长度、分辨率和控制强度受模型限制；
- 同一段视频重复运行可能得到不同白模，影响可复现性。

#### 方式 B：控制视频到视频生成

系统不让模型自由理解整段视频，而是先把视频转成结构化条件：

```text
原视频
  -> pose/depth/edge/mask/camera
  -> video diffusion + ControlNet-like branches
  -> 白模视频
```

这样做的目的，是把“原视频的结构”与“输出视频的外观”分开。控制图并不一定直接可见；它们更像模型生成过程中的中间约束。

这条路线适合当前项目的第一版，因为它的交付物就是一个可作为 `reference_video` 的视频，不要求把每个物体恢复为正式的 3D 资产。

### 3.5 时间一致性不是附加项

逐帧生成会带来严重的时间问题。白模视频至少需要检查：

- 同一个人是否在相邻帧变成不同体型；
- 道具和墙体是否闪烁、变形或突然消失；
- 关节是否发生不符合动作的跳变；
- 镜头推进是否变成随机抖动；
- 白灰材质是否在每帧改变明暗和粗糙度；
- 镜头切换处是否出现跨镜头内容污染。

工程上可以组合使用：

- 跨帧注意力或时空 latent；
- 重叠窗口推理和首尾帧约束；
- 光流引导的 latent/feature warp；
- 跟踪 ID 约束；
- 关键帧或参考帧锚定；
- 生成后的视频稳定化和色彩统一；
- 镜头级别而不是整片级别的任务拆分。

因此，“模型能够处理视频”不等于“它能稳定地产出可用于后续生成的白模参考视频”。时间一致性必须有独立的验收指标。

## 4. 路线 B：视频分析后重新渲染白模

这条路线先从视频建立一个可控的中间表示，再输出白模视频。

### 4.1 中间表示

建议把输入视频先转换为以下轨道，而不是直接写成画布节点：

```text
VideoAnalysisResult
- sourceVideoHash
- fps
- duration
- shotSegments
- cameraTrack
- actorTracks[]
- objectTracks[]
- depthSamples
- floorPlane
- confidence
- warnings[]
```

每个 `actorTrack` 至少需要：

```text
trackId
frameRange
2dKeypoints
optional3dPose
position / rotation estimate
occlusion intervals
identity confidence
```

每个 `cameraTrack` 至少需要：

```text
frameRange
position estimate
orientation estimate
focal length estimate
intrinsics confidence
scale convention
```

### 4.2 从轨道拟合程序化白模

第一版不需要恢复真实人体网格，可以使用：

- 胶囊、盒子、球体等 primitive；
- 项目已有的白模演员 archetype；
- 根据身高、骨骼比例和姿态参数生成的程序化角色；
- 地面、墙体和大体积道具；
- 估计出的摄影机和镜头关键帧。

然后把结果映射到 `PrevisScene`：

```text
人物        -> objects[].kind = actor
道具        -> objects[].kind = prop
相机        -> cameras[]
镜头切段    -> shots[]
走位/姿态   -> object keyframes / bone tracks
运镜        -> camera keyframes / cameraMove
```

最后复用预演台已有的白膜渲染器。

### 4.3 这条路线的优点和限制

优点：

- 结果可以被用户在预演台里移动、改姿态、改机位；
- 白膜输出具有确定性，容易重复渲染；
- 可以把动作和相机轨道单独修正；
- 便于生成多个不同角色/场景版本。

限制：

- 单目视频中深度、尺度和相机内参往往不唯一；
- 人物被遮挡时，背面和被遮挡肢体无法直接从视频恢复；
- 道具、墙体和背景很难只靠几帧可靠识别；
- 非刚体物体、布料、头发和特效不适合简单 primitive 拟合；
- 真实视频的每帧误差会积累成漂移、脚滑和穿模。

因此输出应先是“场景候选”或“轨道候选”，让用户确认后再写入正式 `PrevisScene`。不要把不确定的视觉推断直接当成用户已经确认的场景事实。

这条路线的难点不是“能不能从一帧图猜出一个人体”，而是把估计结果放进同一个世界坐标和时间坐标里。WHAM 这类研究会把 2D 关键点序列、视频特征、SLAM 得到的相机角速度和接触约束结合起来，专门处理世界坐标、脚滑和相机运动问题；这正是把视频分析结果映射到预演场景时必须单独建模的部分。[WHAM: Reconstructing World-grounded Humans with Accurate 3D Motion](https://arxiv.org/abs/2312.07531)

场景几何也有类似边界。DUSt3R 说明了可以从无预先标定的图像集合估计点图、深度和相对/绝对相机，但这类研究能力不能直接等同于“任何单目视频都能稳定还原出可编辑的场景工程文件”。[DUSt3R: Geometric 3D Vision Made Easy](https://arxiv.org/abs/2312.14132)

### 4.4 本地 Agent + Blender 的可执行形态

如果目标是得到可编辑的 3D 白模场景，一条常见的自建路线是让本地 Agent 或普通 Worker 负责调度视觉分析工具和 Blender，而不是让浏览器直接完成重建：

```text
视频上传与任务创建
  -> 人物/物体分割、姿态、深度和相机分析
  -> Agent/Worker 生成带版本的轨道与场景参数
  -> Blender Python API 创建或更新网格、骨骼、相机和关键帧
  -> Blender/Eevee/Cycles 渲染白模图片或视频
  -> 保存 .blend / glTF（可选）和 MP4（供参考视频使用）
  -> 后端校验、物化资源并回写画布
```

这里的 Agent 主要承担“选择工具、组织步骤、处理失败和生成脚本”的编排职责；人物跟踪、深度估计、网格拟合和渲染仍由确定性的模型、Python 脚本或 Blender 完成。若第一版只需要白模参考视频，可以不启动 Blender，直接把分析结果送入视频合成/视频生成 Worker；若需要用户在预演台里移动对象、修改相机和重新渲染，则必须保存结构化场景候选。

因此应把产物分成两档：

- `reference_video`：只保证可播放的视频、动作/机位/构图等参考语义和来源元数据；内部是否经过 Blender 不影响调用方合同。
- `scene_candidate`：还要保存对象、骨骼、相机、轨道、坐标系、版本和置信度，并允许用户确认或修正后再写入正式 `PrevisScene`。

不要因为某个产品在界面中显示了胶囊体和方块，就直接把它当作可以导入 Blender 的场景。只有明确导出网格、骨骼、相机或轨道，并验证坐标和时间轴，才可以把结果归入 3D 重建路线。

## 5. 混合路线：最适合产品化的方案

对于当前项目，推荐采用混合架构：

```text
输入视频
  -> 规范化与镜头切分
  -> 轻量分析：姿态 / 深度 / 跟踪 / 相机提示
  -> 选择输出模式
       ├─ reference_video：生成白模参考视频
       └─ scene_candidate：生成可编辑预演候选
  -> 用户确认或修正
  -> 回写画布资源和节点
```

### 5.1 第一版只做 `reference_video`

第一版验收目标应是：

- 能处理短片段；
- 能输出可播放、时长完整的 MP4；
- 人物动作和镜头运动与输入视频大体一致；
- 外观被明显简化成白灰/低纹理表达；
- 可作为后续视频模型的参考视频；
- 失败、取消、重试和超时状态可追踪；
- 不会覆盖源视频，也不会把未确认的推断写入正式预演场景。

### 5.2 第二版再做 `scene_candidate`

第二版可以把分析结果转为候选 `PrevisScene`，但需要：

- 帧范围和镜头边界；
- 人物和道具的可见性；
- 低置信度标记；
- 时间轴缩放和起始帧校准；
- 地面高度和世界尺度校准；
- 相机焦距/视场角手动修正；
- 用户确认后再执行场景 patch；
- 保留原视频和原分析版本，支持重新拟合。

## 6. 与当前项目的对应关系

### 6.1 已有能力：`PrevisScene` 到白膜视频

当前浏览器白膜导出路径是：

- [`previs-clay-materials.ts`](../../web/src/lib/canvas/previs/previs-clay-materials.ts)：创建灰白 `MeshStandardMaterial`，把普通场景 mesh 临时换成白膜材质；预演演员展示层和带 shader uniforms 的 mesh 会被跳过。
- [`previs-viewport-capture.ts`](../../web/src/components/canvas/previs/previs-viewport-capture.ts)：使用 `canvas.captureStream()` 和 `MediaRecorder` 录制视口，并检查实际录制时长。
- [`canvas-previs-workbench.tsx`](../../web/src/components/canvas/previs/canvas-previs-workbench.tsx)：播放镜头、录制 WebM、转 MP4、捕获 beauty 帧并调用 `onApply()`。
- [`use-canvas-previs.ts`](../../web/src/pages/canvas/use-canvas-previs.ts)：创建“白膜视频”画布节点，设置 `workflowKind: "reference_video"`，并物化 `assetId`。

这条链路的输入是结构化预演场景，不是外部视频。

### 6.2 已有能力：参考视频进入视频生成模型

当前项目已经有“把参考视频传给视频模型”的协议适配：

- [`video.ts`](../../web/src/services/api/video.ts) 接收 `ReferenceVideo[]`，按模型能力校验参考视频并创建/轮询视频任务。
- [`video-provider-seedance.ts`](../../web/src/services/api/video-provider-seedance.ts) 会把参考视频转换为 URL 或 data URL，并在支持的协议中发送为 `reference_videos` 或 `reference_video`。
- [`provider_protocol_request.go`](../../backend/internal/app/provider_protocol_request.go) 将视频引用的角色固定为 `reference_video`。
- 当前还支持 `videoEditOperation: "reference_to_video"` 这一类视频编辑语义，但它代表把参考视频送给上游模型，不代表系统先做了白模化。

这意味着新增功能可以把输出白模视频直接接入现有参考视频合同，但仍需要一个独立的转换任务来产生这个中间产物。

### 6.3 当前没有的能力

当前没有发现以下业务主链：

```text
CanvasNode(Video)
  -> 视频帧分析
  -> 姿态/深度/相机/分割
  -> 白模视频生成
  -> output asset
```

也没有发现：

```text
VideoWhiteModelJob
  -> VideoAnalysisResult
  -> PrevisScene candidate
```

媒体转换节点的操作类型是图片转换；当输入类型是视频时，代码会把状态设为 `unavailable`，错误码为 `video_not_ready`，提示视频转换尚未开启。见 [`media-conversion-node.tsx`](../../web/src/components/canvas/nodes/media-conversion-node.tsx) 和 [`contracts.ts`](../../web/src/lib/media-conversion/contracts.ts)。

## 7. 面向当前项目的实现设计

### 7.1 建议的产品入口

不要把“视频转白模”伪装成当前图片媒体转换节点的一个普通选项。它有独立的：

- 输入视频和片段裁剪；
- 任务进度；
- 上游模型或本地流水线；
- 资源占用和配额；
- 失败恢复；
- 结果预览；
- 作为参考视频使用的后续动作。

更合适的入口是：

```text
画布视频节点
  -> 操作菜单：生成白模参考视频
  -> 创建后台任务
  -> 任务完成后生成新的视频节点
  -> 与源视频建立 reference/derived 关系
```

源节点和结果节点都要保留，不要原地覆盖源视频。用户可能需要比较原片、白模参考和最终生成结果。

### 7.2 建议的任务合同

以下是面向新功能的建议合同，不是当前已经存在的 API：

```text
POST /api/video-white-model/jobs

请求：
- sourceAssetId
- sourceNodeId
- clipStartMs / clipEndMs
- mode: reference_video | scene_candidate
- style: clay | blockout | wireframe
- preserve: motion | camera | blocking | timing
- model / provider selection
- idempotencyKey

响应：
- jobId
- status
- acceptedSourceHash
- estimatedDurationMs
- limits
```

状态读取和控制建议为：

```text
GET  /api/video-white-model/jobs/:id
GET  /api/video-white-model/jobs/:id/events?after=<seq>
POST /api/video-white-model/jobs/:id/cancel
POST /api/video-white-model/jobs/:id/retry
```

任务记录至少应包含：

```text
VideoWhiteModelJob
- id
- userId
- canvasId
- sourceAssetId
- sourceNodeId
- sourceVideoHash
- sourceDurationMs
- clipStartMs / clipEndMs
- mode
- style
- preserveFlags
- provider / model
- status
- stage
- progress
- outputAssetId
- outputNodeId
- outputDurationMs
- sourceAnalysisVersion
- errorCode / errorMessage
- attemptGroupId
- createdAt / updatedAt
```

如果生成了结构化分析结果，再单独保存：

```text
VideoAnalysisResult
- jobId
- shotSegments
- cameraTrackRef
- actorTrackRefs
- objectTrackRefs
- depthArtifactRef
- confidenceSummary
- warnings
- algorithmVersion
```

不要把几万帧的姿态和深度 JSON 直接塞入画布文档。大结果应作为版本化资源或压缩轨道保存，画布只保存引用和用户确认后的摘要。

### 7.3 任务执行边界

推荐的服务关系：

```text
浏览器
  -> 上传源视频并创建 job
Go 后端
  -> 鉴权、资源准入、任务 admission、幂等、计费/配额、事件和结果物化
转换 Worker 或外部视频模型
  -> 解码、分析、生成/渲染、转码
Go 后端
  -> 校验结果、保存 output asset、发布终态事件
浏览器
  -> 创建白模参考视频节点并显示结果
```

第一版可以把重计算委托给支持视频到视频或参考视频控制的上游模型；后端仍然要负责任务事实、输入输出资源和终态。不要让浏览器长时间持有唯一的轮询状态。

当前 [`video.ts`](../../web/src/services/api/video.ts) 的 `requestVideoGeneration()` 有固定轮询次数和 provider-specific 间隔。它适合已有前端生成入口，但新功能不应把“浏览器轮询上限到达”当成“上游任务失败”。用户已经反馈过“视频实际上可以成功，但等待超时先报错”的问题；白模转换应使用持久化任务状态、可恢复轮询和终态事件，避免同类误报。

### 7.4 资源和并发

如果使用外部视频模型，服务器主要承担：

- 源视频上传和临时/长期存储；
- 代理或签名 URL；
- 任务状态、事件和重试；
- 结果下载、校验和物化；
- 资源清理与引用保护。

对当前项目而言，这意味着外部模型路线的压力主要是**网络、磁盘和任务协调压力**，不是每个白模任务都在本机占用一张 GPU。真正需要重点控制的是上传/下载带宽、临时文件生命周期、结果重复下载、任务并发、上游限流和失败重试。浏览器播放或预演台的 Three.js 白膜渲染主要消耗用户电脑资源；后端仍要承担上传、保存、鉴权和最终资源落盘，但不应把浏览器正在渲染误算成服务器 GPU 负载。

如果自建分析/生成流水线，服务器还承担：

- 视频解码和抽帧 CPU；
- 姿态、深度、分割和跟踪模型的 GPU/CPU 推理；
- 视频扩散或渲染 GPU；
- FFmpeg 编解码；
- 多任务显存隔离和队列调度。

至少要有：

- 每用户并发任务限制；
- 全局 GPU worker slot；
- 输入时长、分辨率、文件大小和帧率上限；
- 取消后真正停止推理或标记输出不可提交；
- 任务租约和 worker fencing；
- 结果资源的校验、哈希和引用；
- 上游提交成功但响应丢失时的恢复状态。

不能用一个 HTTP 请求的长连接超时来代替这些任务边界。

可以把两种部署方式的资源账单先这样理解：

| 部署方式 | 单个任务的主要资源 | 并发扩展的主要瓶颈 | 第一版建议 |
| --- | --- | --- | --- |
| 外部视频到视频服务 | 上传带宽、对象存储、结果下载、任务状态 | 上游配额、网络出口和本地存储 | 优先用于验证功能价值 |
| 自建 Worker / ComfyUI / Wan VACE | GPU 显存和推理时间，另加解码、转码 CPU | GPU slot、显存碎片、队列长度和模型装载 | 有稳定 GPU 后再接入 |
| 当前预演台浏览器录制 | 用户电脑的 WebGL、编码和内存 | 用户设备性能、浏览器录制限制 | 继续作为结构化场景的白膜出口 |

无论采用哪一种部署方式，任务状态都必须持久化。上游已经接受任务但客户端连接断开、浏览器刷新或一次轮询达到上限时，系统仍应能够通过任务 ID 继续查询、接收回调、恢复结果下载和完成资源物化；“客户端这次等超时”只能表示本次等待结束，不能直接把任务写成失败。

## 8. 白模结果如何供后续视频生成使用

白模转换完成后，结果应作为普通视频资源，但带有明确的来源和用途元数据：

```text
reference_video_node
- assetId
- sourceVideoNodeId
- sourceAssetId
- sourceVideoHash
- workflowKind: reference_video
- referenceKind: white_model
- preservation: [motion, camera, blocking, timing]
- conversionJobId
- provider / model
- conversionVersion
- durationMs / fps / width / height
```

接下来由视频生成入口把它放入 `ReferenceVideo[]`。提示词应说明参考视频的职责，例如：

```text
参考视频仅用于保持人物动作、走位、镜头运动和时间节奏。
将参考视频中的白模角色替换为指定角色，保留镜头构图和动作顺序。
不要继承参考视频的白灰材质、几何简化外观或原始人物身份。
```

如果上游模型支持不同的参考视频角色，应把“动作参考、镜头参考、风格参考、首帧/尾帧”区分成独立字段。当前项目已经有 `reference_video` 这一层协议角色，但没有白模转换任务自身的角色和版本字段。

## 9. 质量评估与验收

### 9.1 自动指标

第一版至少应记录：

- 输入/输出时长差；
- 实际帧率和分辨率；
- 解码、编码和音视频轨完整性；
- 姿态轨迹相似度；
- 相机运动或全局光流相似度；
- 人物/道具跟踪 ID 的连续性；
- 帧间闪烁和亮度波动；
- 输出中源人物身份/服装纹理的泄漏程度；
- 任务耗时、显存峰值、失败阶段和重试次数。

“输出文件存在”只能证明物化完成，不能证明它适合作为运动/构图参考。

### 9.2 人工验收素材集

建议准备至少六类短片：

1. 单人固定机位；
2. 单人推拉或横移；
3. 多人交叉和遮挡；
4. 快速运动和运动模糊；
5. 明显道具交互；
6. 硬切、闪白或多镜头混剪。

对每类素材检查：

- 动作顺序是否保持；
- 人物数量和相对位置是否保持；
- 相机方向和运动是否保持；
- 白模外观是否统一；
- 是否有明显闪烁、穿模、脚滑、身份交换；
- 作为后续视频生成参考时，模型是否按预期继承运动而不是继承原始外观。

### 9.3 回归测试分层

建议分四层：

| 层 | 核心验证 |
| --- | --- |
| 纯函数/协议 | 参数归一化、片段裁剪、状态机、参考视频 metadata、幂等键 |
| Worker 集成 | 解码、抽帧、控制信号产物、失败恢复、取消和资源清理 |
| HTTP 黑盒 | 创建、查询、事件、取消、重试、权限、重复请求、终态 wire format |
| 真实素材验收 | 多种镜头和人物条件下的运动、镜头、白模外观和时间一致性 |

当前仓库已有的视频生成测试和任务恢复测试不能自动证明“视频转白模”通过；需要新增针对白模任务的固定短片夹具和结果判定。

## 10. 不应采用的实现方式

### 10.1 只把视频转成灰度

灰度只改变颜色，不会保留或显式控制动作、深度、相机和人物关系，也不能阻止后续模型继承原视频纹理。

### 10.2 只在提示词中写“白模”

提示词可以描述目标外观，但无法单独保证逐帧动作、相机轨迹和时间一致性。至少需要参考视频输入和某种结构条件。

### 10.3 把每一帧当独立图片生成

这会导致闪烁、身份交换、形体漂移和镜头不连续。视频模型或后处理必须拥有跨帧机制。

### 10.4 直接覆盖源视频节点

白模是派生参考物，应该能追溯到源视频、转换参数和任务版本。原地覆盖会破坏比较、重试和资源回收。

### 10.5 把视频转换当成浏览器本地小工具

当前项目的浏览器本地路径适合预演视口录制和短时 FFmpeg WASM 转码；长视频分析、姿态/深度推理和视频扩散应使用持久化任务和受控 worker/上游服务。

## 11. 推荐实施顺序

### P0：定义并冻结中间产物

- 定义 `reference_video` / `white_model` 元数据；
- 定义源视频、转换任务、输出资源和派生节点关系；
- 定义状态、取消、重试、幂等和超时语义；
- 定义“完成”和“仅上传成功”的区别。

### P1：接入一个外部视频到视频/参考视频能力

- 只支持短片段和一种白模风格；
- 使用后端任务，不把浏览器轮询作为事实源；
- 输出 MP4 并物化到资源系统；
- 通过现有 `ReferenceVideo` 进入后续视频生成；
