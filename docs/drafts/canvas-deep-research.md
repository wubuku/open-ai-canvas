# 画布系统深度调研报告

> 这是一份**研究草稿**，但它的读者不是本仓库的维护者，而是**一个正准备自己动手写一套 AI 视频创作画布的人**。
>
> 假设你不用 React，也不用 Go。你可能用 Vue + Spring Boot，也可能用 Svelte + Rust。本文不关心这些。本文只回答一个问题：
>
> **当你要把「剧本 → 分镜 → 图片 → 视频 → 成片」这条链路做成一块可无限扩展的二维画布时，这块画布内部应该长成什么形状，以及哪些设计决策是必须在写第一行代码之前就定下来的。**
>
> 全部结论来自当前仓库源码、配置与测试的静态阅读。本轮没有启动前后端服务、没有真实模型调用、没有跨设备同步和浏览器刷新验收。文中「已实现」指源码中存在完整调用路径或有针对性测试；需要真实环境才能确认的行为单独标注为「待验证」。

### 0.2 三个最小前提

在读后面的架构之前，先确认你已经理解这三件事。如果还不理解，先看 1.1 和 2.1：

1. **画布是一份 JSON 文档**，不是一个组件树。整张画布序列化后是带 `nodes` / `connections` 数组的一个对象。
2. **节点的大部分状态挂在一个 `metadata` 对象上**，而不是分散在节点顶层字段上。
3. **同一个「完成」在不同层含义不同**。任务成功不等于节点已更新，节点已更新不等于云端已保存。

## 1. 核心结论：画布不是编辑器，是七种状态

### 1.1 七层状态模型

如果只记住一件事，请记住这句话：

> **AI 创作画布的核心难点不是画图，而是同时维护七种互不等价的状态，并且知道它们各自什么时候才算「完成」。**

当前项目把这七种状态分散在不同层，但它们必须被明确区分：

| # | 状态层 | 事实源 | 「完成」的含义 | 常见误判 |
| --- | --- | --- | --- | --- |
| 1 | 编辑器即时状态 | 页面内的 `nodesRef` / `connectionsRef` | 当前这一帧的操作对象是最新的 | 以为它已经写进任何持久层 |
| 2 | React 渲染快照 | 页面 `useState` | 组件已经重绘 | 以为它已经落盘 |
| 3 | 本地文档 | 按用户作用域隔离的浏览器数据库 | 当前浏览器 profile 已写入 | 以为云端也已保存 |
| 4 | 云端文档 | 服务端画布接口，带 `revision` 和 ETag | 服务端已确认本次写入 | 以为浏览器看到的就等于云端 |
| 5 | 生成任务 | 后台任务系统里的一次生成作业 | 上游模型已产出终态 | 以为任务成功就等于节点已更新 |
| 6 | 资源物化 | 存储标识（`storageKey`）加资源接口 | 字节已落盘，可被重新解析出访问地址 | 以为节点上的预览字段有值就等于文件存在 |
| 7 | 素材绑定 | 素材 ID（`assetId`）加素材库同步 | 素材库已承认这张媒体 | 以为素材库有图就等于画布节点已保存 |

这张表是全文所有架构结论的根因。绝大多数「画布 bug」在根上都是**有人把其中一种状态当成了另一种**。真实的故障长这样：

- 用户说「素材库里有这张图，但画布上没保存」。真相：第 7 层成立，第 3、4 层没成立。
- 用户说「我明明加了节点，刷新就没了」。真相：第 1、2 层成立，第 3 层的写入被跳过或冲突丢弃。
- 用户说「生成成功了，节点还是空的」。真相：第 5 层成立，第 6 或第 7 层没成立。
- 用户说「节点不见了」。真相：只是第 1 层的视口裁剪把它隐藏了，数据完好。
- 用户说「一生成就把别的节点改了」。真相：有人用旧的完整节点数组覆盖了当前文档。

**给重做者的第一条建议**：在写第一行 UI 代码之前，先把这张表打印出来。并且为你即将编写的每一个「保存」「生成」「上传」「同步」函数，在注释里标注它修改的是第几层，以及它什么时候才允许宣告完成。

下表是全文的浓缩版。每一行都对应后面某一节的详细论证。

| # | 结论 | 详见 |

## 2. 数据模型：谁是事实源

### 2.1 顶层文档

一张画布是一个对象，不是节点数组。顶层字段大致是：

```text
CanvasProject
  id / projectId / title / createdAt / updatedAt
  revision / remoteContentHash          <- 同步身份，不是 UI 版本号
  nodes[] / connections[]               <- 内容主体
  chatSessions[] / activeChatId          <- 会话也是文档的一部分
  viewport / appearance / backgroundMode <- 可保存，但不影响内容身份
  previsScenes[] / timeline?             <- 结构化创作产物，各有独立事实源
```

这里有两个容易忽略的设计决定：

**第一，`viewport` 属于文档但不属于内容。** 视口是「我现在看到哪里」，不是「文档是什么」。这一点在第 5.5 节会展开：判断两份文档是否相同时必须剔除视口，否则用户只是滚了一下视图就触发了一次同步。

**第二，会话也在文档里。** 画布内置的助手会话和节点、连线共享同一份持久化和同一套合并算法。这带来一个真实的好处：撤销、冲突合并、多标签页协调只需要一套机制。但也带来一个真实的成本：会话消息的冲突合并逻辑必须和节点分开写，因为它们的粒度和冲突形态不同（第 4.5 节）。

### 2.2 节点：身份极简，状态极重

节点本身的形状非常小：

```text
CanvasNodeData
  id          <- 稳定身份，创建后永不改变
  type        <- 内置类型或插件贡献的运行时类型
  title       <- 人类可读，可随时改
  position / width / height / parentId  <- 几何与容器归属
  metadata?   <- 几乎所有业务状态
```

这个划分本身就是一个值得借鉴的决定：**节点顶层字段只放「画布语义」，其他一切放 metadata。** 好处是几何操作（移动、缩放、框选、折叠、对齐）可以在完全不碰业务状态的前提下运行。坏处是 metadata 会变成一个巨大的松散字典，这是第 2.3 节要处理的问题。

重做时值得考虑的一个改进：把 `position` / `width` / `height` 拆到独立的 `layout` 对象或独立的坐标存储，让「移动节点」在数据库层面是一个极轻量的操作，而 metadata 完全不动。这在并发冲突时可以显著降低冲突面积。本项目没有这样做，因此节点移动会和 metadata 修改在同一个合并粒度上冲突。

### 2.3 metadata 是最大的风险区

`metadata` 上挂着的东西非常多。按所有权分组，至少有：

| 分组 | 代表字段 | 生命周期 |
| --- | --- | --- |
| 编辑态输入 | `content`、`composerContent`、`prompt` | 用户每次输入都在变 |
| 媒体身份 | `storageKey`、`mimeType`、尺寸、时长 | 资源物化时写入 |
| 素材绑定 | `assetId`、`assetTags`、`assetCategory` | 素材库同步时写入 |
| 任务绑定 | `taskId`、`taskStatus`、`taskProgress`、`taskErrorCode` | 一次生成任务期间 |
| 模型选择 | `model`、`producedModel`、`producedModelCandidate` | 选择时和产出时分别冻结 |
| 生成配置 | `generationSpec` | 声明式、无凭据 |
| 批次关系 | `isBatchRoot`、`batchRootId`、`batchChildIds` | 批次创建时建立 |
| 插件命名空间 | `pluginId`、`pluginNodeId`、`pluginData` | 插件生命周期内 |
| 结构化子文档 | `storyboard`、`batchTable`、`generationBatches` | 见第 9 节 |

**这张表隐含了一条最重要的纪律：同一时刻属于不同所有者的字段，不能被同一个写入路径整体覆盖。**

本项目对此的处理方式是分散的但有效的：每条写入路径只认自己那几个字段。生成回写只合并生成相关字段；移动节点只改几何；素材同步只改素材字段。真正需要写全文档的路径只有三个：初始加载、历史恢复、显式导入。

如果 metadata 里出现了「每条路径都要判断一下自己要不要动这个字段」的代码味道，正确的做法是把它拆开。可以拆的方向：把任务绑定拆成 `taskBinding` 对象，把媒体身份拆成 `mediaRef` 对象，把生成配置保持为独立的 `generationSpec`。这样类型系统就能帮你守住边界，而不是靠人记住。

重做时另一个值得注意的字段对：`model`（下次生成使用的模型）和 `producedModel`（当前产物实际的模型）。它们必须分开，因为用户在生成之后改下拉框，不应该改变已经产出内容的事实。同理还有 `producedModelCandidate`：已提交但尚未成功落盘的模型身份。这三者的区分在计费追溯和结果可解释性上很有价值。

### 2.4 连线携带语义，不是纯几何

连线对象包含起止节点、句柄、锚点比例，以及一个可选的关系字段：

```text
CanvasConnection
  id / fromNodeId / toNodeId
  fromHandleId / toHandleId          <- 哪个输入槽
  fromAnchorRatio / toAnchorRatio    <- 锚点位置，用于绘制
  relation?                         <- 语义标记
  storyboardRowId?                  <- 行级连线指向具体的分镜行
```

`relation` 当前有四种取值：`storyboard-output`、`storyboard-asset-reference`、`batch-output`、`batch-input`。这不是装饰。带不同 `relation` 的连线在生成时的含义完全不同：

- 普通媒体输入：参与参考素材解析，参与提示词拼装，影响容量校验。
- `batch-input` / `batch-output`：只表达批次分组关系，**不是**媒体输入。
- `storyboard-output`：分镜行到产出节点的归属关系。
- `storyboard-asset-reference`：分镜行对素材的引用。

这个区分是本项目踩过坑之后才补上的：早期实现把父批次到子图的分组边也当成媒体输入，导致子图的第二张参考图丢失。详见 [画布批量生成一致性治理](../design/canvas-consistency-repair.mdx)。

**给重做者的建议**：在你画第一根线之前，先回答四个问题，并且把答案写进类型里。

1. 这根线是否可见，怎么画？
2. 这根线是否允许建立？
3. 这根线是否参与提示词或参考素材解析？
4. 这根线是否只是分组关系，不应被当作媒体输入？

如果第 3 和第 4 都能为真，那么你的连线类型必须至少有两个变体，而不能是一条带若干布尔标记的记录。否则你会在解析函数里写满 `if (relation !== "batch-output")` 这样的例外。

### 2.5 生成合同需要双端同源

节点上的 `generationSpec` 是一份**声明式、无凭据**的生成合同：模式、提示词、模型选择、参数选项、参考绑定、文本输入模式。它刻意不包含渠道密钥、真实路由和计费信息。

这份合同在前后端各有一份定义，Go 侧是权威来源，通过 `go:generate` 生成 TypeScript 声明文件。这样做的收益是：

- 前端可以做本地校验并给出即时反馈；
- 后端可以做最终校验并拒绝伪造请求；
- 两侧的字段名、类型和枚举不会各自漂移。

**这是本文最推荐直接照抄的一个小设计。** 它成本极低（一个生成命令加一个结构体定义），收益是消除一整类「前端能过、后端 400」的 bug。如果你用 Vue + Java，做法完全一样：Java 侧定义 DTO 和校验器，生成 TypeScript 类型，或者退一步用 JSON Schema 作为共享契约。

合同里还有几个值得注意的常量，它们体现了对 AI 画布典型失控场景的防御：`MaxPromptRunes` 限制提示词长度、`MaxNodeTitleRunes` 限制标题、`MaxCanvasOperations` 限制单次批量操作数。**在合同层设上限，比在每个调用点检查可靠得多。**

## 3. 前端运行时：命令式引用与声明式渲染的分工

### 3.1 为什么需要两套写入路径

AI 画布的交互密度远高于普通文档编辑器：拖拽、框选、多选批量移动、连线、生成中取消、任务回调、Agent 推送变更，全部可能同时发生，且都要求立刻反映到界面上。

如果只用 React 状态，一个致命问题是：**React 的状态更新函数可能被重新执行。** 而画布的编辑动作往往带副作用（写 ref、触发保存、发请求）。让框架重放一个带副作用的更新函数，等于让同一个副作用执行两次。

本项目的解法是把写入拆成两条路径：

```text
用户操作 / 键盘 / 拖拽
  -> 命令式写入（createCanvasStateWriter）
       1. 同步改 ref（nodesRef.current = after）
       2. 再把同一份快照 publish 给 React
       3. React 收到的是「结果」，不是「另一个待执行的动作」
```

这个模式的名字在很多框架里都有等价物（命令式句柄加不可变快照），关键不在名字，而在**两条不变量**：

1. 命令式路径是唯一的真相来源，React 只是订阅者。
2. 全量替换快照的权限只授予「加载」「恢复」「导入」这类明确操作，异步回调没有这个权限。

第二条不变量是本项目付出过代价才确立的。第 6 节会讲为什么。

### 3.2 页面是编排层，不是实现层

本项目的画布页面把流程拆成了一批页面级 hook，各管一件事：生命周期、选择、视口、连线、上传、生成、历史、预演、时间线、批量表。页面本身负责把这些 hook 组装成一个工作区。

这个分层对重做者的价值在于：**它让「生成」和「连线」这样的复杂流程可以被单独测试和替换，而不需要启动整个页面。**

如果你在 Vue 里做同样的事情，对应做法是把画布页面的状态组合逻辑抽到 composable 层，而不是全部写在模板和组件里。一个可用的判断标准是：**如果你无法在不挂载完整页面组件的情况下测试「连线是否合法」，说明编排逻辑还留在组件里。**

### 3.3 纯函数层是重做者最该抄的部分

本项目把几乎所有画布业务逻辑抽成了不依赖 React 的纯函数：文档比较、内容哈希、空间索引、可见性选择、LOD 决策、连接策略、引用解析、批次表格、分镜操作、布局计算。

**这是本文推荐抄的第二件事，而且它比第一件事更值钱。**

原因很简单：这些函数是**可单测的**。本项目的画布相关前端测试基本都覆盖这一层。当你在 Vue + Java 的世界里重做时，对应的目标形态是一样的：

- 前端有一套不依赖框架的纯函数层（视图变换、几何、引用解析、文档变换）。
- 后端有一套不依赖 HTTP 框架的领域层（准入校验、资源归属、合同校验）。
- 两侧都有针对纯函数的测试，且这些测试不需要启动应用。

如果你的纯函数层足够厚，UI 层就退化成「把纯函数的结果画出来」，那整个系统的可测试性和可推理性会完全不同。

## 4. 本地持久化：多标签页、失败写入与三方合并

这一节是普通白板也会遇到的经典难题，但 AI 画布把它放大了，因为 AI 画布会持续产生异步写入。

### 4.1 存储必须按用户作用域隔离

本项目的画布主体存储在浏览器的结构化数据库里，逻辑键是固定的，但实际落盘前会经过一个作用域函数改写成带用户标识的物理键，读取时用同样规则还原。因此两个账号即使在同一浏览器里，也不会读到对方的画布。

**这一点很容易做漏**：如果你只在逻辑层面区分用户，而没有在物理存储键上隔离，那么用户切换时的残留读取几乎必然发生。

**这不是可选优化，是数据安全底线。** 如果你的应用支持多账号，忘记做作用域隔离会导致：用户 A 登出后，用户 B 看到用户 A 的画布。这类 bug 在测试环境很难发现，因为通常只有一个测试账号。

同时，大对象（画布主体、素材、大 JSON）不应该放进 `localStorage`。`localStorage` 是同步的、有容量限制的、存字符串的，放一个大画布文档进去会在每次读写时阻塞主线程。IndexedDB 是异步的、能存结构化值、容量大得多。

小配置（当前主题、当前作用域、上次打开的画布 ID）可以放 `localStorage`，但要清楚它的定位是「偏好」，不是「文档」。

### 4.2 本地文档需要自己的版本号

本项目在本地存储的文档外层包了一层元信息：

```text
CanvasStorageDocument
  state.projects          <- 画布数组
  version                 <- 存储格式版本
  storageRevision         <- 本地文档修改序号
  savedAt                 <- 上次写入时间
  journalTokens           <- 各写入者的去重令牌
  tombstones              <- 各实体的删除标记
```

`version` 让你可以在未来改变存储格式时做迁移。`storageRevision` 是本地世界的单调递增序号，它让「我基于哪个版本做的修改」这件事可以被回答。这两个字段看起来不起眼，但它们是后面所有合并算法能够正确工作的前提。

### 4.3 多标签页写入必须串行化

同一个用户可能在两个标签页打开同一张画布。如果两个标签页同时写本地存储，后写的会覆盖先写的，而且不会有任何提示。

本项目用一个持久化锁把写操作串行化：所有对本地文档的写入都要先获取锁，锁内完成「读当前 → 合并 → 写回」。这意味着**读-改-写是一个临界区**。

这个锁有两层：同一页面内用 Promise 队列串行化（保证本标签页的写入顺序），跨标签页用浏览器原生 Web Locks API 按用户作用域加锁（保证多标签页互斥）。如果浏览器不支持 Web Locks，一般保存会降级为仅本标签页串行；但**生成结果的持久化路径会直接报错而不是降级**，因为在无法保证跨标签互斥时写入生成副作用，可能导致同一副作用被重复应用。

**这个降级策略值得抄**：不是所有写入都值得为强一致性付出降级代价，但「生成结果落盘」这种必须幂等的写入，宁可失败也不要冒险。

这不是过度设计。AI 画布的特点是后台写入多（自动保存、生成回写、素材同步、Agent 变更都可能触发保存），不加锁的丢失率在真实使用中一定会出现。

### 4.4 失败写入必须有 journal

写本地存储可能失败：配额满了、标签页被杀掉、用户切走了。关键问题是：**一次写入「准备开始」和「确认完成」之间发生崩溃，你怎么知道它有没有真的写进去？**

本项目的解法是一个 journal：写入开始前在另一个键里记一条「我准备写 token=N」，写入成功后记录「token=N 已完成」。启动或下次写入时，如果发现 journal 里有未完成的记录，就按恢复流程处理。

这是一个成本不高但价值很高的模式。**如果你打算做「本地优先」的 AI 画布，我强烈建议抄。** 它的作用是在崩溃后保持一致性，而不是试图证明「我们不会崩溃」。

### 4.5 合并必须是三方 rebase

这是本地合并的核心算法，也是最容易写错的地方。

朴素的做法是「后写覆盖先写」，但这会丢掉先写的内容。稍微好一点的做法是「按字段合并」，但这在删除和并发新增上会出错。

本项目做的是标准的三方 rebase，有三份文档参与：

- `base`：两份文档共同的祖先（上次同步时的版本）。
- `local`：当前这一份正在写入的文档。
- `durable`：存储里已经落盘的那一份文档。

对每个字段的判断逻辑是：

```text
如果 local 和 base 相同，说明本地没改这个字段  -> 取 durable 的值
如果 durable 和 base 相同，说明存储没改这个字段 -> 取 local 的值
如果 local 和 durable 相同，说明两边改成了同一个值 -> 取这个值
如果三者都不同，说明真的冲突了 -> 有策略地取舍，并记录一个冲突
```

这个算法能够同时正确处理「两边改不同字段」（合并）和「两边改同一字段」（按策略取舍），而不需要显式区分这两种情况。

**这是本文最推荐直接照抄的算法**，因为它有清晰的不变量，容易测试，也容易在出问题时推理。重做时你应该把它当成一个纯函数来写：`rebase(base, local, durable) -> (merged, conflicts)`，然后用大量手写用例覆盖它。

数组实体（节点、连线、会话、消息）需要按 ID 合并，本项目为此写了一个通用的实体合并函数，它处理删除、并发新增和同 ID 并发修改。

### 4.6 删除必须有 tombstone

三方合并有一个经典陷阱：删除会「复活」。

场景：标签页 A 删除了节点 N，标签页 B 还保留着 N。A 写盘时留下「N 已删除」的标记。随后 B 因为某种原因（例如一个无关的字段变更）触发了一次写入，带着它那份还含有 N 的文档。如果合并时只按「B 的 local 里有 N」判断，就会把 N 重新写回存储。

解法是 tombstone：删除时在文档里留一个「实体 ID 已被删除」的标记，合并时如果发现这个标记比 base 更新，就尊重删除。

本项目的 tombstone 是分层的（项目、节点、连线、会话、消息各有一套），并且带序号，这样能判断「哪个删除更新」。这是一个容易被忽略但必须有的设计——**没有 tombstone 的三方合并，在真实多标签页使用中一定会复活已删除的数据。**

### 4.7 少数字段需要特殊合并规则

通用三方合并不是所有字段的正确答案。本项目为两类字段做了特殊处理：

- `updatedAt`：冲突时取 durable，避免用本地时钟污染服务端时间。
- `generationEffectKeys`（幂等键集合）：取并集，而不是按字段冲突处理。因为两个副本可能各自成功应用了不同的副作用，合并时应该保留两个键，否则其中一个副作用会被重复执行。

第二个规则是一个很好的例子：**幂等键集合的正确合并语义是并集，不是覆盖。** 如果你用普通字段合并，你会得到「A 以为自己已经应用过的副作用在 B 上重新执行」。

## 5. 云端同步：revision、ETag、历史与内容身份

### 5.1 revision 是单调递增的服务端版本

云端每张画布有一个 `revision`（整数）。写入时客户端提交自己知道的 `revision` 作为基准，服务端检查：如果当前服务端 revision 和客户端基准不一致，说明中间有别人（或另一个设备）写过，服务端拒绝这次写入（冲突）。

这实现了**乐观并发控制**。它比「最后写入者获胜」安全，因为「最后写入者获胜」会静默丢弃前一个写入者的修改，而用户不会知道自己丢了东西。

当前项目的服务端在 revision 冲突时返回错误，前端据此进入冲突处理流程，而不是无条件覆盖。

**给重做者的建议**：即使你的第一版只做单人单设备，也应该从第一天就把 revision 放进数据结构。事后补加的成本远高于一开始就加上。

### 5.2 ETag 让「未修改」可验证

读取单张画布时，服务端返回一个 ETag，形如 `W/"canvas-<revision>"`。客户端下次读取带上 `If-None-Match`；如果画布没有变化，服务端返回 304，客户端就知道「我手里的还是服务端那份」。

这个机制的价值在于**它把「我是不是最新的」从客户端猜测变成了可验证的事实。**

**对比**：如果客户端只能用时间戳或者内容哈希自己判断，它必须假设自己的时钟是准的、或者承担一次完整下载来验证。ETag 是服务端给的权威答案。

注意本项目的 ETag 是基于 revision 的弱 ETag（`W/` 前缀），因为画布的内容身份本身由 revision 表达。

### 5.3 写入必须带基准 revision

和读取对称，写入也要带基准。客户端提交 `revision`，服务端用它做检查。

这里有一个容易被忽略的细节：**本项目的写入是「整文档写入」**，也就是客户端提交完整的画布 JSON，服务端替换。这意味着并发写入的粒度是整张画布，而不是单个节点。

**这是一个明确的简化，也是当前项目的一个已知局限。** 如果两个人同时编辑同一张画布的不同节点，整文档写入会让其中一个失败（revision 冲突），而不是自动合并。

对于「一个人或少数几个人编辑一张画布」的场景，整文档写入加乐观锁是合理的选择。它实现简单，冲突语义清晰。**但如果你预期多人大画布协作，你需要的是更细的写入粒度**（比如按节点提交变更，或者引入 CRDT / OT）。这是一个需要你根据自己的协作模型提前决定的架构分叉点。

### 5.4 历史快照要同时保护资源引用

本项目在画布写入时会保存历史快照。这不是简单地存一份旧 JSON——快照还要记录它引用的资源 ID。

为什么重要？因为资源（图片、视频）是独立于画布文档存储的，遵循「删除前检查引用」原则。如果一个资源的唯一引用来自某个历史快照，那么在删除资源时也必须把这些快照算进去。

本项目在保存快照时会收集画布文档引用的资源 ID，把它们和快照一起保存，并在删除资源时做全局引用检查。这意味着：**历史快照不仅保护「内容」，还保护「资源的存在」。**

这个设计很值得抄。如果你的画布支持「删除媒体但可从历史恢复」，那你必须让历史快照参与资源的引用计数，否则会出现「历史里有个节点指向一张已经被删掉的图」。

### 5.5 内容哈希必须排除视口

当前项目用一个内容哈希来判断「两份画布文档的内容是否相同」，用于决定是否跳过保存。计算哈希前必须剔除：视口、`updatedAt`、`revision`、远端内容哈希本身。

理由是：**视口的移动、外观主题的切换、同步字段的更新，都不是内容变更。** 如果不剔除，用户只是滚了一下视图，就会触发一次「内容变了」的判断，进而触发不必要的同步或保存。

这是一个很小但收益很高的细节。它反映了一个通用原则：**任何「是否需要同步」的判断，都要先把「不影响内容的状态」剥离出去。**

性能上也有一个小设计：本项目对规范化的内容做缓存，用不可变对象引用（WeakMap）做键，只在内容字段真正变化时重新计算哈希。这避免了每次渲染都重新序列化整张画布。

## 6. 生成任务与结果回写：AI 画布的核心难点

这是本文最重要的一节，也是 AI 画布区别于普通白板的地方。如果你只读一节，请读这一节。

### 6.1 生成是异步的，编辑是同步的

普通白板的写操作是「用户操作 → 立刻反映」。AI 画布多了一个环节：生成是异步的，可能要等几十秒到几分钟。这中间用户会继续做别的事：移动其他节点、编辑提示词、删除某个节点、开始另一次生成。

这产生了一个本质困难：**当生成结果终于回来时，如何把它写回，而不至于覆盖用户在等待期间做的修改？**

### 6.2 浏览器提交的模型配置不是事实源

这是一个最重要的安全边界，也是 AI 画布必须从第一天就建立的原则。

当浏览器发起生成请求时，它会提交一堆配置：选了什么模型、什么尺寸、什么质量、带什么参考图。**这些都不能被信任。**

服务端必须独立完成一套准入校验：

- 输入标准化和合法性检查；
- 用户权限和功能开关；
- 逻辑模型到具体渠道的路由解析；
- 模型能力是否支持请求的操作；
- 额度、计费和并发准入；
- 资源引用是否属于当前用户。

本项目把这套准入集中在任务创建入口，并且在 Worker 执行时再校验一次。

**这意味着：即便用户伪造请求，浏览器显示的「模型」也不是最终计费和执行的模型。** 页面展示的模型、实际执行的模型、最终计费的模型，全部来自服务端的同一份目录和路由。

**给重做者的建议**：把你的生成请求设计成「用户表达意图」，而不是「用户指定执行细节」。让服务端决定「用什么模型跑」。这同时解决了安全问题（用户不能指定任意模型）、成本问题（服务端可以路由到最便宜的合适模型）和一致性问题（前端展示和服务端执行不会不一致）。

### 6.3 提交阶段：指纹与幂等

前端在提交生成前会计算一个「请求指纹」，并用它防止同一个节点在同一次意图下重复提交。提交的数据里区分了「用户正在编辑的内容」和「实际发给模型的有效提示词」——这两者经常不同（比如用户输入了模板变量但没填完）。

指纹的用途是幂等：如果同一个指纹已经在提交中或已提交，就不重复发请求。这避免用户双击或者网络重试导致重复计费。

### 6.4 异步结果的危险：旧快照覆盖新编辑

这是本项目付出过真实代价才修复的问题，我用一个具体场景说明。

```text
t0: 节点 A 提交生成，代码在提交时快照了整个节点数组（S0）
t1: 任务在后台跑，用户把节点 B 从 (100,100) 移到 (300,300)
t2: 任务完成，回调拿着 S0 里的完整节点数组写回 —— 节点 B 的移动被覆盖
```

问题的本质是：**回调跨越了一个长时间异步等待，却持有等待之前的完整文档快照。**

本项目为此建立了一条规则：**异步结果只能做最小增量合并，不能做全量替换。**

### 6.5 最小增量合并的具体规则

回写时按节点身份逐个处理，规则如下：

```text
1. 找到目标节点的当前版本（live）。如果找不到（用户已删除）-> 拒绝回写，不复活
2. 检查任务绑定：如果 live 已经绑定了另一个 taskId -> 拒绝回写
3. 计算这次结果真正改变了哪些字段（对比 before 和 result）
4. 只把这些字段合并到 live 的 metadata 上
5. 保留 live 的几何：位置、尺寸、以及用户是否手动调整过尺寸
6. 保留 live 的标题：如果用户在等待期间改过标题
```

实现上，核心函数接收四个参数：当前完整文档、提交时的节点快照、准备好的结果、任务 ID。它返回合并后的新文档，而不是原地修改。

注意第 3 步：**先算「这次真正变了哪些字段」，再合并。** 如果你直接用「结果节点的 metadata 覆盖当前 metadata」，你会把用户在等待期间做的其他 metadata 修改（比如手动调整了画风设置）也覆盖掉。

这条规则也适用于任何异步回调：Agent 推送的变更、任务中心的重试结果、协作编辑的远端更新——凡是跨越异步等待并且持有旧快照的写入，都必须走最小增量合并。

### 6.6 幂等效果键是必需品

在多次重试、断线重连、多标签页的场景下，同一个生成结果可能被「应用」多次（比如任务中心推送 + 恢复扫描 + 手动刷新都命中了同一个已完成任务）。

如果每次都应用，会产生重复插入、重复消耗素材绑定配额、甚至重复触发下游动作。

本项目的解法是给每个生成副作用一个稳定的「效果键」，并把已应用的效果键记录在节点 metadata 上。应用前先检查这个键是否已经应用过；已应用则跳过。

合并效果键集合时取并集（见第 4.7 节），因为不同副本可能各自成功应用了不同的副作用。

**这是本文强烈推荐的模式。**「副作用幂等键 + 已应用集合」这个组合，比任何「标志位」都可靠：它可以精确地防止每个具体副作用的重复执行，而不是笼统地「防重复」。

### 6.7 批次父节点是子结果的投影

批量生成（比如「用这一张图生成 10 个不同姿势」）在数据模型上有一个陷阱：父节点和子节点。

一个常见的错误设计是：父节点也持有任务 ID 和状态，父节点的状态是子节点状态的汇总。

本项目明确了：**父节点是子图结果的投影，不持有独立的任务身份。** 父节点的状态永远是从当前子图重新计算出来的。

这么做的好处：

- 没有「父任务成功但某个子任务实际失败」的状态不一致可能。
- 刷新恢复时不需要同时恢复父任务和子任务两套身份，只从子图重建父状态。
- 两张成功三张失败这种混合结果能被正确表达。

**给重做者的建议**：如果你要支持批量生成，把「父是子投影」作为硬规则。它会替你避免一整类状态同步 bug。

## 7. 资源完整性与素材库边界

这一节讲的是「字节、素材、节点」三者的关系。它是数据安全底线。

### 7.1 媒体身份不依赖预览是否恢复

一个微妙的坑：节点上的媒体内容通常有两个字段——一个是「当前能显示的内容」（比如一个 blob URL 或 data URL），一个是「存储标识」（`storageKey`）。

刷新页面时，预览 URL 需要重新解析，可能失败或延迟，但存储标识仍然有效。如果你的逻辑用「有没有预览内容」判断「节点是否持有媒体」，你会在预览恢复失败时误判节点为空，甚至把它当作可删除的占位。

**本项目的规则：有 `storageKey` 的节点，即使预览暂时为空，也不能当作空节点。** 存储标识存在不等于文件一定能读出来，但它是「曾经物化过」的硬证据。真正读取失败要报错，而不是静默当作没有。

这是本文推荐的一个很小但很重要的规则。它属于「区分状态」的范畴：预览是否恢复是第 2 层，存储标识是第 6 层，两者不能混用。

### 7.2 原地重生必须先解绑旧素材

这是一个具体但极有价值的 bug 模式。

场景：一个图片节点当前绑定素材 A（`assetId = X`）。用户在这个节点上「原地重生」，得到新图片 B，上传到存储得到新 `storageKey`，然后回写节点。

如果回写时保留了旧的 `assetId = X`，节点就变成「旧素材 + 新资源」的配对。服务端校验会发现「这个素材 ID 和这个存储资源对不上」，然后**永久拒绝**这个节点的保存——用户从此无法保存这张画布，而且这个状态很难自查。

**规则：新媒体结果必须清掉旧 `assetId`，把它交给「入库」或「修复」路径按新资源重新绑定。**

本项目在生成回写里显式地把 `assetId` 设为空。**给重做者的启示**：任何「资源被替换」的场景，都要检查是否有「指向旧资源的引用」需要一起清理，否则你会在服务端校验层埋一个永久性 bug。

### 7.3 删除前必须检查业务引用

素材和资源不能被随意删除，因为它们可能被画布节点、生成任务、历史快照引用。删除前必须检查这些引用，有引用就拒绝并返回引用来源。

本项目还区分了「删除素材记录」和「删除物理对象」：物理删除失败时不能删除素材记录（否则用户就彻底找不到它了）。

这是一个通用的数据完整性原则：**记录的删除和物理文件的删除是两件事，任何一方失败都不能造成另一方已删除的不一致状态。**

## 8. 连线、引用与「什么算参考素材」

### 8.1 输入解析必须中心化

「这个节点生成时用了哪些参考素材」这个问题，在本项目里被多个入口需要回答：节点面板显示提示词预览、提交生成、Agent 读取上下文、连接合法性校验、容量校验、批量表引用列。

如果每个入口各自遍历连线数组自己判断，你会很快得到不一致的答案——这正是本项目早期 bug 的成因。

本项目的做法是建立一个统一的引用解析层，它负责：

- 区分媒体输入连线与分组连线；
- 按连线顺序给参考素材编号（这个顺序影响提示词里的「第 1 张参考图」对应哪张图）；
- 去重；
- 防止批次成环；
- 应用特定节点类型的优先级规则（例如配置节点的输入优先）；
- 解析角色卡这类跨类型覆盖的资源引用。

**给重做者的建议**：在你画第一根线之前，先写「引用解析」这个纯函数，并给它写完整的测试。提示词预览和生成提交必须调用同一个函数，否则用户看到的和模型收到的不一致。

### 8.2 连接策略是校验函数，不是 UI 逻辑

本项目把「这条线是否允许建立」实现为一个纯校验函数，它考虑：

- 目标节点是否接受这种输入类型（基于节点注册表声明的接受/拒绝类型）；
- 媒体类型是否兼容（图片节点不能接参考视频）；
- 数量是否超过上限；
- 当前选中模型是否支持这种输入（音频模型的能力差异）；
- 是否会形成批次循环。

一个值得注意的细节：这个校验函数需要知道「当前实际会路由到哪个模型」，因为同名模型组里不同成员支持的输入不同。校验时用的是路由后的结果，而不是下拉框里显示的名字。

**这是「显示的模型」和「实际执行的模型」必须同源的一个具体体现**（见第 6.2 节）。如果你在前端校验时用了错误的模型信息，用户会看到「无法连接」，但换个模型实际是能跑的。

### 8.3 角色卡是跨类型覆盖

角色卡是一个特例：它的 `content` 字段可能为空，但它通过 `workflowKind === "character"` 承载结构化的角色设定和形象引用。它作为参考素材时，需要在普通节点注册表查询之前被特殊处理。

这类「某个节点的类型和它的行为不一致」的情况，是 AI 画布的常态（剧本节点、分镜节点、批量表节点都有类似情况）。**建议你在设计时把它们显式建模成一个判别联合（discriminated union），而不是靠 `if (node.type === X)` 到处判断。**

## 9. 结构化创作产物：分镜、批量表、时间线、预演

### 9.1 不要把所有东西塞进节点 metadata

本项目在这个问题上做过一个正确但未被完全贯彻的决定：**分镜有结构化行（`StoryboardRow`），不是 Markdown。**

一个分镜节点内部包含一个镜头行数组，每一行有二十多个字段（剧情、对白、景别、情绪、光线、镜头运动、时间节拍、图像提示词、视频运动提示词、连续性输出、负面提示词、素材绑定、关键帧时间、生成的图片节点 ID、生成的视频节点 ID、状态、错误详情、关联的预演场景）。

**给重做者的建议**：如果你的产品有「结构化文档」需求（分镜表、剧本大纲、镜头列表），一开始就用结构化字段，不要先用 Markdown 存着「以后再解析」。当前项目专门加了校验来拒绝「只用正文冒充分镜」的写入，说明这个坑踩得很实。

### 9.2 行级身份

分镜行的 `id` 是独立的身份，不是节点 ID。连线可以指向具体的行（`storyboardRowId` 字段）。Agent 操作分镜时必须使用读取结果里的行 ID，不能把节点 ID 当行 ID 用。

这是一个很好的身份分层示例：**节点是容器，行是内容单元，行有自己的生命周期（生成、失败、重试）。**

### 9.3 批量表也是结构化子文档

批量创作表节点内部有：操作类型（换装/创意）、并发数、内容类型（普通内容/分镜）、可选的分镜行、全局提示词、参考图列、文本列、行数组、是否 AI 生成（动态表头）。

参考图列通过带前缀的句柄 ID（`batch-reference:<columnId>`）连接，这允许一张表有多个参考列，而不是固定的几个。行输入和输出也通过专用句柄区分。

**教训**：当你的画布支持「表格型节点」时，不要用普通连线语义表达表格的列引用。用带类型的句柄 ID，解析会清晰很多。

### 9.4 其他结构化产物

- **时间线**（`TimelineProject`）：字幕条目、高亮区间、样式，有自己的类型定义。
- **预演场景**（`PrevisScene`）：3D 预演台的场景、镜头、对象、相机、灯光、动画。预演有自己的快照哈希和 patch 机制。
- **绘图文档**：tldraw 或 Excalidraw 引擎，有独立的文档 ID、修订号和预览存储，不复用普通图片存储。
- **风格档案**：项目级画风快照，包含预设 ID、修订号、资产决策（参考/兼容/阻断），执行时会因为模型不支持而阻断或降级。

这些产物的共同点：**它们有自己的身份、自己的事实源、自己的版本规则，不应该被降级成「某个节点的 metadata 字符串」。**

## 10. 节点能力：前后端两套注册表

### 10.1 为什么需要两套

前端需要知道节点类型的长相和行为：叫什么名字、什么图标、多大、能拉多小、锁不锁比例、生成模式是什么、有哪些输入槽。这些用于渲染和交互。

后端（Agent、任务系统）需要知道节点的能力边界：用途是什么、适合和不适合什么场景、可以更新哪些字段、连接策略是什么、有哪些副作用。

这两组信息**部分重叠但不完全相同**，而且消费者不同。本项目因此维护两套：

- 前端：`web/src/lib/canvas/node-registry/`，一份节点类型定义，包含 UI 信息。
- 后端：`backend/internal/canvas/capability/`，一份能力描述符，包含用途、权衡、可更新字段、连接策略、投影字段。

### 10.2 服务端那套是权威

**这是本文强调的一条纪律**：任何需要「知道节点能做什么」来做出安全决策的地方，必须用服务端那套。不要在前端、提示词或 Skill 里另建一份可写节点白名单。

本项目的服务端能力描述符还带版本号和集合版本号，用于让 Agent 判断自己看到的工具集合是否变化。

### 10.3 能力描述符应该包含什么

本项目的能力描述符包含这些字段，这个清单本身很有参考价值：

```text
标识：type, version, label
用途：purpose, goodFor, notIdealFor, tradeoffs   <- 让 Agent 知道什么时候不要用这个节点
动作：actions
几何：defaultWidth, defaultHeight
生成：inputKind, generationMode
连接：CanSource, CanTarget, AcceptedInputKinds, RejectedInputKinds, MaxInputCount
更新：CanUpdate, PatchFields（每个字段有类型和长度限制）
投影：ProjectionKind, ProjectionField   <- 决定它向 Agent 暴露什么摘要
```

`goodFor` / `notIdealFor` / `tradeoffs` 这三个字段很有意思：它们不是技术约束，而是**给 Agent 的建议**。一个只描述「我能做什么」但不描述「我不适合什么」的能力描述符，会导致 Agent 在不合适的情况下选择它。

`PatchFields` 带类型和长度限制，意味着 Agent 的更新操作是**受 schema 约束的**，而不是自由文本。**这是把 LLM 输出约束在安全边界内的有效手段。**

## 11. 渲染性能：空间索引、LOD 与预算

### 11.1 问题规模

一张创作画布可能有几百到几千个节点，每个节点可能带图片或视频预览。全部挂载 DOM 会让浏览器崩溃。

### 11.2 三个正交的优化维度

本项目的性能优化分三个互相独立的维度，这个分法本身值得借鉴：

**维度一：空间索引（决定「哪些节点和连线可能在视野内」）**

本项目用均匀网格（默认格子 1024）把节点和连线包围盒索引起来，视口查询只返回格子覆盖的候选。超大节点单独处理（超过阈值格子数就单独登记）。查询后恢复原始顺序，保证堆叠行为可预测。

连线也建立同样的索引，并且把折叠的批次子图和折叠容器内的连线排除。

**维度二：LOD（决定「每个可见节点渲染到什么精细程度」）**

本项目有三档：

- `shell`：只渲染外壳，不渲染内容。
- `preview`：渲染轻量预览。
- `full`：渲染完整内容。

LOD 决策考虑三个因素：是否在视野内、是否在进入缓冲区、是否正在编辑。正在编辑的节点永远 `full`。缩放级别有一个滞后阈值（进入概览用 0.23，退出用 0.27），防止在边界反复挂载/卸载编辑器。

**维度三：预算（决定「屏外预加载多少」）**

预算不是一个固定数字，而是**随缩放级别变化的函数**：缩得越远，能“看得出差别”的节点越少，预算越紧。这样在概览模式下会自动省掉大量细节渲染，回到正常缩放时再补回来。

另外有一类节点被**强制渲染**，不参与预算竞争：当前选中的节点，以及正在拖拽预览中的节点。这和上一条「屏内节点不按预算截断」是同一个原则的两面——**用户正在感知的节点，性能优化不许动。**

这里有一个本项目踩过坑后修正的重要规则：**预算只能裁剪屏外预加载，不能裁掉屏内节点或正在交互的节点。**

本项目早期版本先按预算截断候选列表，再过滤不可见节点，导致真实屏内节点也可能因为预算被挤掉而「消失」。修复后先做语义过滤（视野、隐藏、折叠），屏内和交互节点不按预算截断，预算只限制屏外预加载。

**这个教训对重做者非常重要**：性能优化中的「裁剪」必须区分「用户能感知的东西」和「用户感知不到的东西」。前者绝对不能被预算裁掉。

### 11.3 视口变换与渲染分层

本项目把渲染分层：世界层（节点和连线）、覆盖层（小地图、Dock、浮动控件）。视口变换通过 CSS transform 应用，并且区分「已提交缩放」和「实时缩放」以避免精度问题。

缩放期间还会派发预览事件，让绘图引擎等重渲染组件用较低的分辨率先渲染一帧，然后等缩放稳定后再渲染高清版本。

### 11.4 视口只决定绘制，不决定数据存活

这是一条必须明确的边界：**可见性选择的结果只影响渲染，绝不能修改节点数组或持久化内容。**

排查「节点消失」类问题时，必须分别核对：任务终态、资源是否存在、编辑器节点数组、已保存画布、视口渲染列表。这五者可能各不相同，而它们中的任意一个都可能被人误认为是「节点丢了」。

## 12. Agent、插件与 Skill 如何接入

### 12.1 Agent 读写画布的三道防线

云端 Agent 能读写画布，但它不是「拿到整个 JSON 随便改」。本项目的边界是：

```text
1. 快照：Agent 先读当前画布状态，拿到一个带哈希的快照
2. 结构化操作：Agent 提交结构化的操作列表（创建节点、更新字段、移动、建立连接），不是任意 JSON
3. 后置校验：执行后检查目标节点、连线数量、布局重叠、资源状态是否达到预期
```

操作会经过服务端能力注册表验证：来源节点、目标节点、输入类型、句柄、结构化行引用。Agent 不能删除节点、不能写任意 metadata、不能写媒体 URL 或存储键。

这里有一个容易混淆的点：**前端的操作契约类型比 Agent 实际被允许的操作更多。** 前端共享的操作类型里包含删除节点和删除连线，但服务端提供给 Agent 的工具结构体只声明了「新增节点、更新节点、建立连线」，并在代码注释里明确不接受通用 metadata、媒体 URL 和删除。

也就是说，**「画布支持的操作」和「Agent 被允许的操作」是两个不同的集合，必须分别定义。** 如果你用同一个 schema 同时服务 UI 和 Agent，你就把 UI 的全部能力暴露给了模型。

**给重做者的建议**：如果你要让 Agent 操作画布，把它的写入接口设计成「有限的、声明式的操作集合」，而不是「文档 patch」。前者可校验、可审批、可撤销；后者什么都可能发生。

### 12.2 乐观并发与快照哈希

Agent 每次写操作都必须提交它读到的最新快照哈希。如果画布在 Agent 思考期间被用户改了，Agent 的写入会被拒绝并要求重读。

这是一个很好的设计：**它把「Agent 基于旧认知做出的修改」这个经典问题变成了一个可检测、可恢复的显式冲突。**

### 12.3 插件节点的数据隔离

插件贡献的节点类型用运行时插件 ID 作为持久化类型，数据放在 `pluginId`、`pluginNodeId`、`pluginData` 的命名空间里。插件通过宿主 API 读写画布，写操作进入结构化指令，不直接改宿主内部状态。

插件不能绕过用户归属、任务准入、计费、资源引用保护或出站请求防护。

### 12.4 Skill 不是权限

本项目有多个「Skill」概念，需要区分清楚：

- 产品内的 Skill：版本化的工作流参考材料，供 Agent 或画布技能节点使用。
- 画布 Skill 节点：一种节点类型，快照包含模板、输出模式、输出合同。
- 项目级 `.agents/skills`：代码仓库里的协作者技能文档，和产品运行时无关。

**共同的原则：Skill 提供工作流知识和参考材料，但它不能授权任何操作。** 工具权限、节点能力、审批、预算、资源归属永远由服务端代码决定。

**给重做者的建议**：如果你打算让 LLM 通过「技能文档」获得新能力，务必把「知识」和「权限」分开。Skill 文本只能影响方法论，不能影响授权。

## 13. 测试地图

本项目的测试分布本身就传达了「哪里最容易出错」这个信息。

### 13.1 前端测试集中在纯函数层

画布相关的前端测试几乎都测纯函数：空间索引、可见性选择、连接可见性、连线创建策略、引用解析、批次连接、批次表格、分镜、生成提交、生成回写、存储一致性、远端 revision、编辑器一致性、条件请求、Agent 画布操作和 patch。

**这个分布本身就是结论**：画布的难点在逻辑层，不在渲染层。

### 13.2 后端测试集中在并发和边界

后端测试覆盖：画布 revision 冲突、历史快照并发、资源修复、素材引用、能力注册表校验、任务创建准入、任务执行、计费边界、存储准入、任务恢复、任务输出、媒体身份、任务取消。

注意其中大量是**并发测试**和**边界测试**，不是普通的 CRUD 测试。这反映了画布服务的真实风险在哪里。

### 13.3 一致性集成测试的形态

本项目有一个值得一提的一致性测试形态：它调用真实的生成消费逻辑、真实的 store、真实的锁和 revision 合并，只替换浏览器存储和资源输入，然后模拟两份结果并发提交、落盘期间新增和移动节点，最后重新读取存储验证用户编辑全部保留。

**给重做者的建议**：为你的合并算法和异步回写写这类「替换掉 I/O 但保留全部逻辑」的集成测试。它比单元测试更能捕获真正的数据丢失。

## 14. 排障路径

这一节是给接手这套系统的人（和 Agent）的实用索引。

### 14.1 「节点不见了」

按顺序核对五件事，不要跳步：

1. 任务终态是什么？
2. 资源是否真的物化了（`storageKey` 是否能解析出字节）？
3. 编辑器节点数组里有它吗？
4. 已保存的画布文档里有它吗？
5. 视口渲染列表里有它吗？

如果第 3 步有、第 4 步有、第 5 步没有，那是渲染裁剪问题，不是数据丢失。

### 14.2 「保存没生效」

按顺序核对：

1. 本地写入是否成功（journal 是否有未完成记录）？
2. 远端写入返回的 revision 是多少？是否发生了 revision 冲突？
3. 冲突处理逻辑走的是哪条分支？
4. UI 显示的同步状态是「本地已保存」还是「云端已同步」？

### 14.3 「生成成功但节点没变」

按顺序核对：

1. 任务是否真的终态成功？
2. 结果是否命中了当前节点的任务绑定（有没有被更新的任务顶掉）？
3. 效果键是否已经被应用过（跳过是正确行为）？
4. 回写是否因为「目标节点已删除」被拒绝？
5. 资源物化和素材绑定是否都完成了？

### 14.4 「素材有但画布没有」

这几乎总是因为把第 7 层当成了第 4 层。素材库同步和画布节点保存是两条独立路径。需要确认：素材入库是否完成、画布保存是否完成、两者是否在同一批次里。

### 14.5 「多标签页丢失编辑」

检查持久化锁是否真的覆盖了所有写入路径，以及三方合并的 `base` 是否是真正的共同祖先。

## 15. 实施清单：如果你要自己写一套

如果你准备动手，这里是把本文压缩成的检查清单。每一条都对应本文的一个结论。

### 阶段一：数据模型（先做完这一阶段再写任何 UI）

- [ ] 定义文档顶层结构，明确哪些字段是内容、哪些是视图偏好。
- [ ] 定义节点身份规则：ID 稳定、类型可扩展、metadata 分组。
- [ ] 区分「选择的模型」「产出实际的模型」「已提交未产出的模型」。
- [ ] 定义连线语义，让分组关系和媒体输入是不同变体。
- [ ] 决定媒体身份字段（存储标识）和预览字段是分开的。
- [ ] 给结构化内容（分镜、表格）用结构化字段，不用 Markdown 兜底。
- [ ] 决定写入粒度：整文档还是按实体。这决定了未来协作能力的天花板。

### 阶段二：状态分层（这一阶段决定系统上限）

- [ ] 明确列出你的七层状态，以及每层的「完成」定义。
- [ ] 为每个写操作标注它修改哪一层。
- [ ] 实现命令式句柄 + 声明式快照的双写模式。
- [ ] 限制全量替换快照的权限，只给加载/恢复/导入。
- [ ] 为大对象选择 IndexedDB 而不是 localStorage。
- [ ] 为本地存储加用户作用域隔离。

### 阶段三：并发与持久化

- [ ] 实现带版本号和本地修订号的存储文档。
- [ ] 实现持久化锁，让读-改-写成为临界区。
- [ ] 实现 journal，应对写入中途崩溃。
- [ ] 实现三方 rebase 合并算法，并把它写成纯函数。
- [ ] 为删除实现分层 tombstone。
- [ ] 识别需要特殊合并规则的字段（如幂等键集合取并集）。
- [ ] 实现内容哈希，并剔除视图和同步字段。

### 阶段四：云端同步

- [ ] 服务端为文档实现单调递增的 revision。
- [ ] 写入要求客户端提交基准 revision，冲突时拒绝而非覆盖。
- [ ] 读取返回 ETag，支持条件请求。
- [ ] 历史快照同时记录资源引用。
- [ ] 在 UI 里明确区分「本地已保存」和「云端已同步」。

### 阶段五：生成链路

- [ ] 把生成请求设计成「表达意图」，让服务端决定模型。
- [ ] 服务端独立做准入：权限、能力、路由、计费、资源归属。
- [ ] 提交时计算请求指纹防重复提交。
- [ ] **实现最小增量回写：只合并变化字段，保留并发编辑。**
- [ ] 实现副作用幂等键和已应用集合。
- [ ] 为批次设计「父是子投影」的状态模型。
- [ ] 让异步回写走最小增量合并路径，永远不走全量替换。

### 阶段六：资源完整性

- [ ] 媒体身份不依赖预览恢复状态。
- [ ] 资源替换时清理指向旧资源的引用绑定。
- [ ] 删除前检查画布、任务、历史快照的全部引用。
- [ ] 记录删除和物理对象删除是两件事。

### 阶段七：性能

- [ ] 为节点和连线建立空间索引。
- [ ] 实现 LOD 分级渲染，含缩放滞后阈值。
- [ ] 预算只裁剪屏外预加载，不裁剪屏内和交互中节点。
- [ ] 可见性选择只影响渲染，不影响数据。
- [ ] 分离世界层和覆盖层。

### 阶段八：Agent 与插件

- [ ] 后端建立节点能力注册表，作为唯一权威。
- [ ] Agent 写入走结构化操作，不走自由 patch。
- [ ] Agent 写入要求快照哈希，实现乐观并发。
- [ ] Agent 写入做后置校验，不只返回「工具调用成功」。
- [ ] 插件节点数据命名空间隔离。
- [ ] 把「Skill 知识」和「工具权限」彻底分开。

### 阶段九：测试

- [ ] 纯函数层有独立测试，不依赖框架和应用启动。
- [ ] 合并算法用手写用例覆盖删除、并发新增、同 ID 并发修改。
- [ ] 异步回写测试覆盖「目标已删除」「已换任务」「效果键已应用」。
- [ ] 有替换 I/O 但保留全部逻辑的一致性集成测试。
- [ ] 性能测试验证「同屏千节点仍全部可见」。

## 16. 待验证与未覆盖的边界

诚实标注本轮调研的局限：

- 没有启动服务、没有真实模型调用、没有浏览器刷新或跨设备同步的端到端验收。
- 多标签页并发写入的合并算法有单元测试和存储集成测试，但真实浏览器多标签场景未做端到端验证。
- 极端场景（千节点同屏、长时间生成、频繁切标签页）下的性能未做实测。
- 已被旧快照覆盖的历史节点无法自动重建；这类数据只能从历史画布或任务上下文恢复。
- 云端 Agent 的画布操作在本轮只做了静态阅读，未做真实运行验收。

如果要把本文的结论提升为正式文档或作为实现规范，建议先补上跨设备同步、长时间生成和真实浏览器多标签这三个场景的验证。

## 17. 给实现者的最后叮嘱

本文所有架构决策都可以归结为一句话：**区分状态，尊重身份，让异步结果做增量。**

- 区分状态：不要把「本地保存」「云端保存」「任务完成」「资源就绪」混为一谈。
- 尊重身份：节点 ID、任务 ID、资源 ID、素材 ID、效果键、revision、快照哈希，这些身份字段不能被异步回调随意覆盖。
- 让异步结果做增量：跨越异步等待的回调永远只提交自己的变化，保留并发编辑。

如果你在动手时对某个具体决策犹豫，问自己：**这个决定在并发、失败、崩溃三种情况下分别会怎样？** 如果你答不上来，那这个决策还没想清楚。
