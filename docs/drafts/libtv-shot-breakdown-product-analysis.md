## TL;DR

LibTV 的「逐帧拉片」可以较可靠地理解为：把一段参考视频拆成若干可继续创作的参考素材，至少围绕「分镜」「动态」「音乐」三个维度组织结果。公开官网前端资源明确出现了节点名称、描述、输入方式和任务状态文案；多篇产品实测文章进一步描述了关键画面/关键帧、运镜或节奏参考、音频/BGM 以及画布素材组等用户可见结果。

目前不能从公开资料确定它的内部算法、模型、任务 API、输出 JSON 或关键帧筛选规则。「逐帧」不应直接解释成“每一帧都导出一张图”；更稳妥的工程推测是：视频规范化、镜头切分、代表帧筛选、视频/音频理解和素材物化组成一条分阶段流水线。这个判断用于指导我们自己的产品设计，不是对 LibTV 内部实现的断言。

「深度动作捕捉」与「逐帧拉片」在公开产品操作上有关联：教程描述从参考视频的「逐帧拉片」下拉入口选择「深度动作捕捉」，再生成用于后续视频生成的深度/白模类参考视频。但公开证据只证明了菜单和用户工作流的关系，不能证明“逐帧拉片必须先执行”、两者共用一个后端任务，或向用户交付了可编辑的 Blender/FBX/骨骼工程。

对当前项目的直接结论是：现有项目已经有 `PrevisScene` 到白膜视频的浏览器录制路径，也有媒体资源、参考视频和异步任务的基础能力；没有发现与 LibTV「逐帧拉片」等价的“任意输入视频 -> 分镜/动态/音乐素材组”完整主链。若要借鉴，应借鉴“可复核的中间产物和可组合的画布工作流”，而不是照搬具体模型或把外部字段猜成内部合同。

## 2. 官方公开页面核验：能确认什么

2026-10-15 对 `https://www.liblib.tv/` 的页面内容做了独立抓取。HTML 内嵌资源中出现以下键值：

| 前端键 | 公开值 | 能支持的结论 |
| --- | --- | --- |
| `nodeTypeShotBreakdown` | `逐帧拉片` | 产品存在该名称的节点/能力文案 |
| `nodeTypeShotBreakdownDesc` | `拆解视频的风格、运镜与音频` | 官方公开定位涉及风格、运镜和音频 |
| `shotBreakdownMediaSectionLabel` | `视频素材` | 输入被设计为视频素材 |
| `shotBreakdownUploadVideo` / `shotBreakdownPickFromCanvas` | `上传视频` / `从画布选择` | 至少存在上传和从画布选取两种输入入口文案 |
| `shotBreakdownDimStoryboard` | `分镜` | 公开拆解维度之一 |
| `shotBreakdownDimCameraMoves` | `动态` | UI 显示为“动态”，代码键名把它映射到 camera moves；这提示运镜语义，但不等于输出相机参数 |
| `shotBreakdownDimMusicRef` | `音乐` | 公开拆解维度之一 |
| `shotBreakdownStart` / `shotBreakdownRunning` | `开始拉片` / `拉片中` | 存在显式启动和运行中状态文案 |
| `shotBreakdownFailed` / `shotBreakdownVideoNotReady` | `拉片失败，请重试` / `上游视频未就绪` | 产品考虑了失败和上游视频未就绪状态 |
| `shotBreakdownVipOnlyTooltip` | `会员专属` | 页面有会员专属提示；不能据此推导所有账号的实际计费规则 |
| `depthMapRefLabel` | `深度动作捕捉` | 存在相邻的深度动作捕捉能力文案 |
| `depthMapRefResolutionLabel` / `depthMapRefConfirmSubmit` | `清晰度` / `确认提取` | 深度动作捕捉有分辨率选择和确认提交的界面语义 |
| `depthMapRefDurationExceedHint` / `depthMapRef720pDurationHint` | 时长上限提示 | 深度动作捕捉存在按时长/分辨率限制的公开提示 |

这些键值证明的是“产品界面打算提供什么”，不是“后端实际怎样做”。例如，`CameraMoves` 不能证明系统导出了相机外参曲线；`视频素材`不能证明只接受某一种视频编码；`拉片中`不能证明使用轮询而不是事件流。

未登录首页能看到 LibTV 画布、Agent、3D-BOX 等入口，但首页是否展示某个营销卡片不能用来判断功能是否存在。帮助中心或公开 FAQ 没有提供逐帧拉片的完整输出 schema；帮助页中出现的多机位分镜/宫格能力也不能当作逐帧拉片产物样例。

### 3.2 需要主动降级的来源解释

这些文章并不构成完全独立的实验复现：它们可能互相引用、复用同一产品演示或处于同一营销活动周期。因而本文采用以下写法：

- “多篇文章都这样描述”可以作为 L2 的产品行为线索；
- “LibTV 官方一定这样实现”不能从文章推出；

- 文章中的后续模型（例如 Seedance 2.5）说明下游工作流，不说明 LibTV 分析阶段内部使用的模型。

## 4. 三个公开维度应该怎样理解

### 4.1 分镜：较强的方向证据，字段仍不确定

公开资料支持“分镜”会帮助用户看清参考片的镜头组织，并可能产生关键画面/关键帧或镜头素材。当前可以说：

- 产物方向：镜头级参考、代表画面、可能的镜头分组；
- 主要用途：与角色图、场景图等素材组合，继续生成或重组；
- 证据等级：能力方向 L2，具体文件和字段 U/L4。

不能把其他 Agent（例如“爆款复刻”）文章中出现的 16 镜头、时长、景别、机位、光线、声音和替换方案字段，直接当成画布逐帧拉片的输出 schema。它们可能是不同入口、不同模板或人工整理后的展示层。

### 4.2 动态：优先理解为运镜/节奏参考

`shotBreakdownDimCameraMoves` 是目前最具体的官方语义锚点，公开文章也使用“运镜”“动作节奏”“动态参考”等说法。因此，最稳妥的表述是：动态维度提供运动或运镜相关的参考拆解。

下列内容没有被公开证据确认：

- 2D 人体关键点序列；
- 人物跟踪轨迹文件；
- 光流、深度图或姿态序列作为用户可下载产物；
- 相机外参曲线、可驱动骨骼或 3D 动作工程。

“动态”可能只是文字/时间轴/视频片段，也可能包含内部视觉特征；在未看到实际产物前不能选定其中一种。

### 4.3 音乐：至少是音频/BGM 参考，分析深度未知

官方描述含“音频”，UI 有 `MusicRef`，第三方文章提到原始音频、BGM 或声音素材。因此可以记录为：音乐维度至少面向音频或 BGM 的提取/引用。

没有证据证明它一定产出：ASR、歌词、词级时间戳、节拍网格、能量曲线、分离人声或乐器 stems。官网另有背景音、音效、人声等相关文案，不能据此断言这些能力和音乐维度共用同一个任务或输出。

## 5. “逐帧”不等于全量导出每一帧

中文影视语境中的“逐帧拉片”可以指逐帧观看、分析和拆解。现有公开证据更符合“镜头/代表帧级拆解”：

```text
视频输入
  -> 媒体信息读取与必要的规范化
  -> 镜头/场景边界识别
  -> 代表帧筛选和去重
  -> 分镜、动态、音频维度分析
  -> 关键帧、音频和分析结果物化
  -> 画布节点或素材组
```

这是 L3 工程推测，不是 LibTV 内部流程图。它比“10 秒视频按 24/30 fps 输出 240/300 张图片”更能解释以下公开行为：产品使用“关键画面/关键帧”措辞；结果要放回画布继续使用；功能被描述为快捷参考；用户需要能浏览和组合结果。

在自己的实现中，可以保留全部帧作为临时分析输入，但只把代表帧和可复核摘要作为用户层产物。关键帧数量、抽样密度和筛选算法必须通过产品合同或任务配置明确，而不能从“逐帧”这个名字推导。

## 6. 与“深度动作捕捉”的关系

### 6.1 可以确认的产品关系

公开前端文案把“深度动作捕捉”作为一个有清晰度和时长提示的能力。第三方教程多次描述“选中参考视频 -> 从逐帧拉片相关入口选择深度动作捕捉 -> 生成深度/白模类视频 -> 与角色/场景素材连接 -> 后续视频生成”。这足以支持“同一产品工作流中存在关联入口”这一结论。

### 6.2 不能确认的后端关系

以下说法都不能从当前公开证据推出：

- 深度动作捕捉必然先执行分镜/动态/音乐拉片；
- 两者共用一个任务 ID、队列或数据库记录；
- 深度动作捕捉一定复用逐帧拉片的关键帧结果；
- 深度动作捕捉向用户交付 Blender、FBX、骨骼、网格或相机工程；
- 公开文章描述的胶囊体、方块和简单几何体是固定的内部实现，而不是演示视频中的可视化表达。

更谨慎的产品模型是两条可组合的旁路：

```text
同一参考视频
  ├─ 逐帧拉片：镜头/代表帧/动态说明/音频参考
  └─ 深度动作捕捉：深度或白模类参考视频
```

是否共享缓存、是否在 UI 上串成连续向导，应该等登录后真实任务证据确认。

## 7. 最可能的工程实现（推测，不是 LibTV 内部事实）

### 7.1 混合流水线是最能解释公开行为的方案

```text
上传或选择视频
  -> 读取时长、帧率、分辨率、音轨
  -> 规范化转码和预览代理
  -> 镜头切分
  -> 代表帧筛选、质量过滤、重复帧去除
  -> 对代表帧/短片段做视觉理解
  -> 整理镜头、动态、音频的结构化结果
  -> 物化关键帧、音频、摘要和画布引用
```

对于动态维度，可以再按需要调用光流、人物跟踪、深度或相机估计；这些更可能是内部中间产物，不能因为产品显示“动态”就断言会交付给用户。

深度动作捕捉可以是独立任务：

```text
视频
  -> 人物/主体跟踪、深度/姿态/相机估计或视频到视频转换
  -> 代理几何或白灰参考视频
  -> 完整性检查和资源物化
  -> 作为 reference_video 供后续生成
```

这条路线不等于可编辑 3D 重建。只有交付了结构化对象、网格、骨骼、相机轨道并允许用户编辑，才能称为视频到 3D 场景重建。

### 7.2 三种实现路线及其取舍

| 路线 | 做法 | 优点 | 主要限制 |
| --- | --- | --- | --- |
| 轻量分析 + 代表帧 + VLM/LLM | FFmpeg/媒体库负责切镜、抽帧和音频，模型负责理解和整理 | 阶段可观测、缓存容易、产物可复核 | 对复杂动作和长片理解有限 |
| 多模态视频模型直出 | 将短片段交给视频理解模型，直接返回结构化结果 | 语义整合能力强，开发较快 | 成本、时延和失败定位较差；需额外物化证据帧 |
| 混合方案 | 低成本预处理为主，难例再调用视频模型；深度动捕走独立管线 | 最适合可组合画布产品 | 需要管理阶段状态、版本和重试边界 |

如果当前项目借鉴这类能力，建议优先使用混合方案：把中间产物落成可检查的资源和结构化摘要，让用户能局部重做和替换，而不是依赖一个不可解释的端到端黑盒。

## 8. 对当前项目的适配结论

当前项目已有能力和缺口以仓库源码、测试和既有研究为准。可继续从 [`web/src/components/canvas/previs/`](../../web/src/components/canvas/previs/)、[`web/src/lib/canvas/previs/`](../../web/src/lib/canvas/previs/)、[`web/src/services/canvas-video-preview.ts`](../../web/src/services/canvas-video-preview.ts)、[`web/src/services/api/video.ts`](../../web/src/services/api/video.ts)、[`backend/internal/app/provider_video.go`](../../backend/internal/app/provider_video.go)、[`backend/internal/app/task_media_storage.go`](../../backend/internal/app/task_media_storage.go) 和 [`backend/internal/assets/`](../../backend/internal/assets/) 进入实现；这些入口证明相邻的预演、媒体、任务和资源能力存在，但不能反向证明已经存在 LibTV 同名功能：

| 能力 | 当前项目状态 | 不能误写成 |
| --- | --- | --- |
| `PrevisScene` 结构化场景 -> 浏览器 Three.js 白膜视频 | 已有路径，见[预演台系统调研](previs-workbench-deep-research.md) | 任意输入视频都能自动还原成 3D 场景 |
| 取帧、媒体转换、转写、参考视频资源 | 有分散的基础能力，具体入口以代码为准 | 已经具备 LibTV 逐帧拉片的三维结果合同 |
| 画布节点和异步任务 | 有基础能力 | 已经有 `ShotBreakdownResult` 这样的统一模型 |
| 深度/白模参考视频任务 | 当前研究建议和部分相邻能力存在 | 已经实现 LibTV 同等的深度动作捕捉 |

如果要在当前项目新增类似能力，建议把“逐帧拉片”定义成独立的长任务，而不是塞进普通视频生成节点。一个可审计的最小结果可以是：

```text
ShotBreakdownResult
- sourceAssetId / sourceVideoHash
- sourceDurationMs / fps / width / height
- analysisVersion
- shots[]
  - shotId / startMs / endMs / durationMs
  - keyframeAssetIds[]
  - visualSummary / shotSize / cameraMotion
  - subjectSummary / actionSummary
  - audioSegmentRefs[]
  - confidence / warnings[]
- audioAssetIds[]
- transcriptRef?                 # 只有真实启用转写时才出现
- artifacts[]                   # 原始响应、诊断、缩略图等版本化资源引用
```

这只是当前项目的设计建议，不是外部 LibTV schema。画布应保存资源引用、摘要和任务状态；大规模帧特征、光流、姿态序列、模型原始响应等应放在版本化任务/资源存储中。任务状态应能区分上传、规范化、分析、物化、失败、取消和成功，不能由浏览器固定等待时间推断最终失败。

与当前“视频转白模”研究的边界如下：

- 本文研究的是外部产品的“拆解参考素材”工作流；
- [视频转白模调研](video-to-white-model-deep-research.md)研究的是视频级白模参考、3D 预演白膜和当前项目的实现路线；
- 两篇文档可以互相引用，但“逐帧拉片”不等于“视频转白模”，也不等于“视频到可编辑 3D 场景重建”。

## 9. 必须完成的进一步实证

若要把公开推测提升为当前产品分析的强证据，下一轮需要在有权限的测试账号中进行真实浏览器和网络记录：

1. 创建最短、无音频、单镜头、多镜头、多人运动和带 BGM 的测试视频；记录时长、分辨率、编码和帧率。
2. 分别勾选分镜、动态、音乐，以及全部组合；确认是多选还是单选，记录任务 ID、阶段、重试和取消行为。
3. 对同一视频重复运行，比较是否命中缓存；记录任务粒度是一个复合任务还是多个子任务。
4. 下载或读取每类产物：数量、类型、时长、时间码、关联节点、可编辑字段、引用关系和资源大小。
5. 验证关键帧数量与源视频总帧数的关系，区分镜头边界帧、均匀采样和动作峰值采样。
6. 对“动态”产物检查是否只有文字/视频，还是还存在姿态、深度、光流或相机轨道文件。
7. 对“音乐”产物检查原始音轨、BGM、ASR、节拍和音轨分离是否分别存在。
8. 单独运行深度动作捕捉，记录清晰度、时长限制、输出视频、任务资源和是否要求先做逐帧拉片。
9. 在不同会员/权限账号下比较积分账单和会员门槛；不要把 UI tooltip 当作账务事实。
10. 记录上游未就绪、失败、刷新页面、断网、重复提交和超时后的最终状态，确认客户端不会把“暂时未完成”误报为失败。

这些证据完成前，本文中的 L3/L4 内容只能用于架构推演和产品方案设计。

## 11. 结论登记

- **已确认（L1/L2）**：公开产品存在“逐帧拉片”名称；界面文案包含视频输入、分镜/动态/音乐维度、运行/失败状态；公开文章将其描述为可整理关键画面、运镜/节奏和音频/BGM 的创作参考；存在相邻的“深度动作捕捉”入口和深度/白模类参考视频叙述。
- **高概率推测（L3）**：产品更可能使用镜头切分、代表帧、音频处理和视频理解的混合流水线；用户层物化的是少量代表帧和可组合素材，而非所有视频帧。
- **尚未确认（U/L4）**：输出 schema、字段、文件格式、关键帧算法、模型名称、任务 API、计费细则、缓存策略、深度动作捕捉的内部中间表示和是否可编辑 3D 交付。
- **当前项目行动建议**：将外部案例作为“可组合参考素材 + 可复核中间产物”的产品启发；实现前先冻结任务、资源、版本、失败恢复和验收合同。
