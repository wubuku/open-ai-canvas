# 画布来源返回与主从页面状态保留设计调研

> **目的**：定义画布编辑器退出导航与来源页面状态恢复的问题边界，比较实现方案并给出可验收的推荐路线。
> **状态**：设计调研草稿；未自动进入发布文档导航，也不代表实现方案已经定案。
> **证据范围**：静态检查前端路由、工作台外壳、画布列表、画布编辑器的导航出口、画布进入入口、React Query 配置和相关 Zustand 状态；未启动前端或进行真实浏览器验收。本文聚焦登录后的 `/canvas/:id` 编辑器，不把独立的 `/share/canvas/:token` 分享页面混入同一返回合同。

> **重点推荐：采用务实的分级退出策略。** 如果保留来源页面实例只需局部、有限的路由改造（例如从 `/canvas` 列表打开画布），就保留页面；返回时恢复事先定义并纳入合同的现场状态，同时清理导航过程中产生的临时状态。对某个来源页来说，如果要保留现场必须增加全局 Keep-Alive 或复杂状态快照，就使用经过校验的 `returnTo` 回到进入前的内部页面地址，不承诺恢复全部临时状态。直接访问画布时使用稳定 fallback。不要为了覆盖所有页面而默认缓存整个应用。

## 结论

### 已确认

1. 左侧「自由画布」导航进入 `/canvas`；具体画布编辑器进入 `/canvas/:id`。
2. `/canvas/:id` 会隐藏工作台全局侧栏和顶部栏，因此用户看到的是全屏画布编辑器；外层路由布局本身仍然存在。
3. 画布顶部菜单里的「主页」固定跳转 `/`，不是浏览器后退，也没有读取进入来源。该菜单还提供单独的「画布」入口；画布工作区轨道也有固定的「主页」链接，项目上下文和项目侧栏还有返回项目概览、项目画布列表、项目设置或章节等明确目标，加载失败和删除画布也有各自的 fallback。因此不能把所有离开画布的操作概括为都回到 `/`。
4. `returnTo` 方案可以解决“回到哪个页面”的问题，但单独不能保证恢复源页面的筛选、分页、滚动位置和弹窗等内部状态。
5. 如果产品要求从 `/canvas` 列表打开画布、退出详情后恢复该列表现场，优先考虑“持久父页面 + 详情子页面”的主从路由结构；详情页可以采用横向推入，也可以采用全屏覆盖。这个选择本身只保留仍挂载且纳入恢复合同的父页面状态，不保留其他业务入口的页面现场。
6. 推荐采用分级策略：现有路由结构内能以有限改动保留来源页面实例时，就保留其现场，并处理导航本身设置或关闭的临时 UI 状态；若要保留任意来源页必须引入全局页面缓存或复杂状态快照，则退化为经过校验的 `returnTo`，保证回到进入前的页面地址，不承诺恢复全部临时状态。

### 推断

- 当前固定跳转 `/` 可能是有意保持「主页」语义稳定，也可能是画布从多个入口进入后没有统一来源上下文导致的实现取舍。
- 这不是画布数据持久化本身的问题，主要是路由上下文和来源页面 UI 状态没有形成合同。

### 待确认

- 「主页」是否应该继续表示固定的全局首页，还是改为“返回进入画布前的页面”。
- 产品要求是只恢复来源 URL，还是必须恢复筛选、已加载分页、滚动位置、选中项和弹窗等完整现场。
- 直接打开、刷新或新标签页打开 `/canvas/:id` 时，返回按钮的默认目标应该是 `/canvas` 还是 `/`。

## 问题定义与设计目标

### 问题定义

当前画布编辑器可从多个入口进入；顶部菜单和工作区轨道中的固定「主页」都没有返回来源页的语义，项目上下文、项目侧栏和错误/删除流程则有各自的固定目标。这里讨论的是这些显式出口与动态回源之间的边界，不代表其他离开画布的操作都跳转 `/`。由此需要分别处理两个问题：

1. **来源定位问题**：从 `/` 以外的页面进入时，顶部「主页」入口不会回到那个来源页面。
2. **现场恢复问题**：即使回到正确 URL，也不一定恢复源页面的筛选、分页、滚动位置和临时 UI 状态。

### 设计目标

- 来源明确时，退出画布回到合法的内部来源 URL。
- 来源 URL 包含必要的 `pathname`、`search` 和 `hash`。
- 当源页面是瀑布流列表时，可按产品要求恢复已加载分页和滚动位置。
- 直接访问、刷新、新标签页打开画布时有稳定 fallback。
- 画布打开期间，源页面不会产生意外滚动、点击、焦点或屏幕阅读器串扰。

### 方案判断

| 方案 | 能否回到正确来源 URL | 能否保留瀑布流现场 | 适合定位 |
| --- | --- | --- | --- |
| 固定跳转 `/` | 通常否（来源本来是 `/` 时吻合） | 否 | 当前「主页」菜单行为；不能作为动态回源合同 |
| `navigate(-1)` | 不稳定 | 不稳定 | 临时后退行为，不适合作为最终合同 |
| `returnTo` | 可以 | 默认不能 | 第一阶段修复错误返回页面 |
| `returnTo` + 页面状态持久化 | 可以 | 可以恢复指定字段 | 中等复杂度的渐进方案 |
| 持久父页面 + 详情子页面 | 可以 | 可直接保留父页面中仍挂载且纳入合同的状态 | 适合需要保留 `/canvas` 列表现场的场景；不自动保留其他业务来源页 |

### 初步建议

如果产品只要求“不再回到主页”，先实现 `returnTo`，并保留一个语义明确的固定「主页」入口。

如果产品要求“从 `/canvas` 列表底部打开具体画布，退出后仍在原来的列表位置”，应优先采用持久父页面承载画布列表、详情子页面承载具体画布的主从结构；不要把 `returnTo` 当作完整页面快照方案。若要恢复创作页、项目详情等其他来源页的现场，需要针对那些页面另外设计。

更一般的产品策略可以分两级：

1. **来源现场容易保留时，保留页面实例。** 例如 `/canvas` 列表与 `/canvas/:id` 详情可以共享一个持久父页面；这能以局部路由改造保留画布列表中的筛选、分页和滚动状态，不需要缓存整个应用的所有路由。
2. **保留来源现场需要通用路由缓存或复杂快照时，使用 `returnTo`。** 对创作页、项目详情等画布列表之外的来源，保存并校验进入前的应用内 `pathname`、允许保留的 `search` 和 `hash`，退出时回到该地址。仅当某个来源页有少量关键状态且容易恢复时，再为它单独增加状态快照；不把任意 React 页面状态都纳入通用序列化合同。

这里的“相对简单”指只保留边界清楚的来源页/父页面，不引入跨所有业务路由的 Keep-Alive 容器；也不要求为任意组件状态建立序列化、过期、账号隔离和恢复时序机制。

## 视觉隐藏与页面保留的区别

以下两种实现看起来可能完全一样，但行为不同。

### 只隐藏导航并替换主内容

```text
列表组件卸载
左侧导航隐藏
画布组件挂载
```

关闭画布后，列表需要重新挂载，组件自己的搜索、筛选、分页和滚动状态可能重新初始化。

### 保留列表并切换详情页

```text
列表组件继续挂载
左侧导航和画布列表组成来源页
画布详情作为子页面进入
来源页和详情页通过横向推入或全屏覆盖切换可见区域
```

关闭画布时只退出详情子页面，列表实例仍然存在，因此列表中仍挂载且未被导航逻辑清理的状态可以直接恢复；这不自动涵盖被显式关闭的抽屉、被清空的 pending 标记或父页面之外的状态。

“左侧导航和画布列表左移、画布详情从右侧进入”是这一模型的具体视觉实现。滑动动画本身不是状态保留的原因；真正的原因是来源页组件在详情打开期间没有卸载。

当前工作台外壳中，左侧导航和主内容区的结构分别位于 `web/src/components/layout/app-top-nav.tsx` 的侧栏区域和 `{children}` 区域。切到 `/canvas/:id` 后，外壳仍挂载，但侧栏因 `hideChrome` 条件被卸载；路由 `Outlet` 中的列表页也被详情页替换。若只要求恢复 `/canvas` 列表现场，持久父页面可承载列表；若还要求保留侧栏实例，则还需调整外壳的条件渲染。判断页面状态是否保留，必须检查具体组件是否仍在 React 树中，不能只看 URL 或外壳是否存在。

## Safari 与移动浏览器风险

以下是实现全屏 Overlay 时需要提前纳入设计和验收的风险清单。它们是工程风险假设，不代表当前仓库已经完成 Safari 验收。

### 视口与安全区域

- 移动 Safari 的地址栏会改变可视高度；全屏画布不能只假设固定的 `100vh`。
- 顶部刘海、底部 Home 指示条和横屏圆角区域可能遮挡工具栏。
- 当前工作台已使用 `h-dvh`，但画布内部工具栏、面板和弹窗仍需要统一检查动态视口和安全区域。

### 键盘与输入

- 画布包含文本编辑、Prompt、Agent 和节点搜索等输入场景。
- iPhone/iPad Safari 打开软键盘后，fixed 元素、底部面板和输入框可能发生可视位置变化。
- 键盘关闭后需要确认画布没有残留偏移，退出画布后源列表滚动位置也没有被破坏。

### 滚动锁定与滚动链

- 画布打开时，底层瀑布流不应继续响应触摸滚动。
- 画布内部滚动区域应独立工作，不能在边界处把滚动传递给源列表。
- 需要检查 Safari 的橡皮筋回弹、嵌套滚动和下拉刷新行为。

### 焦点、无障碍和层级

- Overlay 打开后，键盘焦点和屏幕阅读器不应继续访问被遮挡的源列表。
- 关闭画布时，应将焦点恢复到触发画布的原控件。
- 画布工具栏、Modal、Dropdown、Popover、Toast 和源页面之间需要建立明确的层级合同。

### 性能与资源

- 保留源页面意味着列表资源和画布资源同时存在。
- 画布中的图片、视频、Agent 会话和预演模块可能增加移动 Safari 的内存压力。
- 可以保留源页面 UI 状态，但暂停不必要的后台请求、媒体加载和动画，避免把“保持页面”实现成“所有资源持续运行”。

### 最低 Safari 验收范围

1. macOS Safari：列表底部进入和退出画布。
2. iPhone Safari：竖屏、横屏、地址栏展开和收起。
3. iPhone Safari：画布输入框打开和关闭软键盘。
4. 画布内滚动到边界时，底层列表不随之滚动。
5. 画布打开后使用键盘或 VoiceOver，不访问被遮挡的源页面。
6. 连续进入和退出多个画布，观察内存、媒体加载和页面响应。
7. 浏览器后退、刷新、直接访问 `/canvas/:id` 和新标签页打开。

## 设计决策边界

本文给出设计判断，但不替代正式技术方案或 ADR。在以下两点确认前，不应把某个方案当作必须实现的合同：

1. 「主页」是否继续表示固定首页，是否新增独立的「返回来源页」操作。
2. “返回”验收标准是只恢复 URL，还是必须恢复瀑布流分页、筛选、滚动和临时 UI 状态。

如果后续确定采用持久父页面、详情子路由和横向推入，应另建实现设计或 ADR，补充路由结构、状态边界、动画退场策略、资源暂停策略、Safari 验收证据和失败 fallback。

## 概念模型

假设用户正在一个已经加载了很多内容的瀑布流列表底部：

```text
列表页 A：已经加载第 1～10 页，滚动条在底部
        ↓ 点击某个画布
全屏画布：/canvas/abc
        ↓ 点击退出
回到列表页 A
```

### `returnTo`：来源导航目标

进入画布时，程序记住一个地址：

```text
returnTo = /projects/123/overview?tab=canvas
```

退出时根据这张“地址卡片”跳回去。

它只能回答：

> 应该打开哪个页面？

它不自动回答：

> 这个页面当时滚动到哪里？已经加载了多少页？打开了哪个弹窗？

因此，`returnTo` 更像浏览器书签，不是页面快照。

### `returnTo` 的传递与生命周期合同

`returnTo` 不应被实现成可以跳转到任意地址的裸字符串。建议把它建模为当前浏览器会话中的短期来源上下文：

```ts
type CanvasReturnContext = {
  pathname: string;
  search?: string;
  hash?: string;
  source?: "canvas-library" | "create" | "project-detail" | "other";
  accountId?: string;
  tabId?: string;
  createdAt: number;
};
```

实现时至少需要满足以下规则：

1. `pathname` 必须是当前应用的相对路径；拒绝外部 origin、协议相对 URL（例如 `//example.com`）和无法解析的值。`search`、`hash` 只保留该来源真正需要的参数，不能把任意查询串原样当作安全合同。
2. 同一标签页内的普通进入优先通过路由 `state` 或等价的受控导航上下文传递，避免把完整来源地址暴露在画布 URL 中。路由 `state` 适合当前历史项内的导航，但不能作为可复制、可深链接的长期来源合同；如果产品明确要求刷新或恢复流程也能找回来源，再增加带账号 scope、标签页标识和过期时间的 `sessionStorage` 记录。不能把未隔离的全局 `localStorage` 当作来源栈。
3. 复制链接、新标签页打开、直接访问和恢复失败时，来源上下文可能不存在或已失效，必须回到稳定 fallback（例如 `/canvas`），不能猜测上一次来源。
4. 账号切换、来源目标已删除或权限失效时，应丢弃来源上下文并重新校验目标；消费一次后应清理或标记已消费，避免连续返回时反复跳转。
5. 编辑器内新建画布若要沿用最初来源，必须显式转发这份上下文；不能从当前 `/canvas/:id` 的路径反推原始来源。上下文本身仍只描述导航目标，不扩大为源页面快照。
6. 来源上下文的清理不能做成一个全局单槽位删除操作。若产品要求显式回源后不再通过浏览器后退回到刚才的画布，显式回源通常应替换当前画布历史项；若还要求浏览器前进能够重新打开画布，则应按历史项或导航标识保存可重入上下文，并分别定义“显式关闭”和“浏览器后退”的行为。

这组规则把“回到哪里”与“保存了哪些页面状态”分开：前者是导航合同，后者仍由持久父页面或来源页自己的状态恢复机制负责。

### 背景路由：来源页与画布层并存

本文用“背景路由”泛指来源页仍在 React 树中、详情层覆盖或推入其上的页面保留模式；这里不是在断言当前仓库已使用某个 React Router `location.state` 背景路由实现。

背景路由可以理解成打开一个全屏弹窗：

```text
底层：瀑布流列表页，仍然存在
上层：全屏画布编辑器
```

用户进入画布时，并不是把列表页销毁，而是把画布显示在它上面。用户退出画布时，只关闭上层画布，底层列表自然重新露出来。

这就类似于：

1. 在文件管理器中滚动到第 10 页；
2. 打开一个文件预览窗口；
3. 关闭预览窗口；
4. 文件管理器仍然在原来的第 10 页和原来的滚动位置。

背景路由的重点不是“记住地址”，而是“原来的页面实例没有被销毁”。

### 保持源页面挂载：状态保留机制

“保持源页面”是实现手段，不是另一个特殊 URL。

当前 `/canvas` 与 `/canvas/:id` 是 `AuthenticatedWorkspaceLayout` 下的兄弟叶路由。两者切换时，外层布局可以继续挂载，但 `Outlet` 中的 `CanvasPage` 会被 `CanvasProjectPage` 替换；返回列表时列表页重新挂载。其他路由树若使用嵌套路由或显式保留页面，生命周期会不同。对当前结构而言：

```text
列表组件卸载 -> 画布组件挂载
画布组件卸载 -> 列表组件重新挂载
```

重新挂载列表时，组件内部的 `useState`、DOM 滚动位置和临时弹窗状态通常都会重新初始化。

若把列表改成详情路由的持久父页面，则：

```text
列表组件继续挂载 -> 画布覆盖显示
画布关闭 -> 列表组件继续显示
```

因此该父页面中的分页、滚动位置、筛选条件和临时状态可以随组件实例保留，前提是这些状态没有被导航逻辑主动重置，且页面没有因为资源策略而重新挂载。它只覆盖被保留在父页面中的状态；其他业务入口的页面仍会因跨路由导航而卸载，不能靠画布父页面自动恢复。

## 当前实现与证据

### 路由与全屏外壳

左侧导航将「自由画布」配置为 `/canvas`：

- `web/src/components/layout/workspace-sidebar-nav.tsx:43-51`

路由表将 `/canvas` 和 `/canvas/:id` 注册为两个独立路由：

- `web/src/router.tsx:184-185`

当路径匹配 `/canvas/:id` 时，工作台外壳隐藏全局侧栏和顶部导航：

- `web/src/components/layout/app-top-nav.tsx:23-24`

因此当前画布编辑器不是“列表页内嵌面板”，而是独立的全屏路由页面。

### 当前“主页”与其他编辑器出口

### 画布存在多个导航入口

代码中有多种打开或切换画布的路径，但它们属于不同的来源类型：

- 从创作页或创作页 Agent 入口打开画布：`web/src/pages/create/index.tsx:856-864`、`web/src/pages/create/creation-agent-entry.tsx:30-50`。来源页在画布列表之外。
- 从短剧项目详情创建画布，以及从项目的画布列表卡片打开已有画布：`web/src/pages/projects/detail.tsx:88-109`、`web/src/pages/projects/detail/canvases.tsx:64-75`。来源页在画布库列表之外。
- 资产页的空态目前只把用户带到 `/canvas` 画布库，而不是直接打开某张画布：`web/src/pages/assets/index.tsx:734`。如果产品要求“资产页 → 画布库 → 具体画布 → 退出后仍回到资产页”，就必须把这条上游来源链显式传递；持久画布父页面本身只能自然恢复画布库页面。
- 从画布编辑器内部通过项目上下文、项目侧栏或工作区轨道离开：`web/src/pages/canvas/canvas-project-top-bar.tsx:183`、`web/src/components/canvas/canvas-project-sidebar.tsx:109-134`、`web/src/components/canvas/canvas-workspace-panel.tsx:101`。这些是固定业务目标，不等同于动态来源返回。
- 在当前画布编辑器内新建画布：`web/src/pages/canvas/use-canvas-project-lifecycle.ts:284-289`。当前检索到的是“新建后进入新画布”，没有发现编辑器内直接从一张已有画布切换到另一张已有画布的导航；如果今后增加这种交互，也应沿用本轮画布会话的原始来源策略。
- 删除当前画布后返回 `/canvas`：`web/src/pages/canvas/use-canvas-project-lifecycle.ts:291-307`。这是明确的生命周期目标，不是动态回源行为。

因此，准确返回不能只改顶部菜单：其他业务页入口要保存并校验内部来源地址；列表入口应回到列表；编辑器内新建画布要决定如何传递最初的来源上下文。当前这些创建/进入导航只构造新的 `/canvas/:id` 路径，没有显式携带该上下文。

页面实例保留也不会自动保留所有原始现场。当前列表卡片进入时会设置 `openingProjectIdRef` 和“正在打开”状态，但源码中未见对应清理；如果列表父页面不再卸载，返回列表时必须显式清除此导航中状态，否则 guard 可能阻止再次打开画布。列表历史抽屉的 `openProject` 则在导航后主动调用 `onClose()`；若产品要求退出后抽屉也保持原样，需要调整这一关闭行为，或明确把抽屉关闭定义为导航后的预期状态。

## 哪些状态能否被 `returnTo` 保留

| 状态类型 | 仅保存 `returnTo` 是否能保留 | 说明 |
| --- | --- | --- |
| 页面路径 | 可以 | 例如 `/projects/123/overview` |
| 查询参数 | 可以 | 前提是把 `search` 一起保存，例如 `?tab=canvas` |
| hash 锚点 | 可以 | 前提是把 `hash` 一起保存 |
| 服务端数据 | 可能 | 返回后可以重新请求，或暂时命中缓存 |
| React Query 已加载分页 | 可能 | 依赖 query key 和缓存生命周期，不应视为可靠页面快照 |
| 搜索、筛选、排序 | 默认不能 | 当前主要是组件 `useState`，不在 URL 中 |
| 已加载第几页 | 默认不能 | 远程列表依赖 Query cache，本地列表依赖组件状态 |
| 滚动位置 | 默认不能 | 这是 DOM 状态，不是 URL 状态 |
| 打开的抽屉和弹窗 | 默认不能 | 当前很多状态是组件内部 `useState` |
| Zustand 全局状态 | 视实现而定 | 如果 store 没有在离开时清空，可以继续存在 |
| 画布内容本身 | 通常可以 | 画布有自己的本地/远端持久化链路，但这和源页面现场是两回事 |

## 实现方案比较

### 方案 A：只使用 `returnTo`

进入画布时记录来源 URL，退出时跳回来源 URL。

**优点**：

- 改动最小；
- 能解决从项目详情、创作页进入后错误回到主页的问题；
- 可以保留路径、查询参数和 hash。

**缺点**：

- 不能保证列表现场恢复；
- 不能保证滚动位置和已加载页数恢复；
- 直接打开画布时需要 fallback；
- 需要覆盖多个画布入口。

适合解决“返回错页面”的第一阶段问题。

### 方案 B：`returnTo` 加源页面状态持久化

除了来源 URL，还保存列表的页面状态，例如：

```text
{
  returnTo: "/canvas",
  keyword: "角色",
  projectFilter: "project-123",
  sort: "updated",
  loadedPages: 10,
  scrollTop: 4820
}
```

这些状态可以放在 URL、Zustand 或 `sessionStorage` 中。

**优点**：

- 不需要立即改变为覆盖式路由；
- 可以逐步恢复筛选、分页和滚动位置；
- 对当前列表页结构的侵入相对可控。

**缺点**：

- 需要为每种列表定义恢复字段；
- 数据变化、分页失效和账号切换时需要校验；
- 不能自动恢复任意组件状态；
- 需要防止旧状态污染新的访问。

适合产品只要求“尽可能回到原来现场”的情况。

### 方案 C：持久父页面与详情子页面

将 `/canvas` 设计为持久的画布工作区父路由：画布列表属于父页面，`/canvas/:id` 属于详情子路由。打开详情时，父页面继续挂载；详情可以从右侧横向推入，也可以作为全屏层覆盖父页面。退出时只关闭详情子路由，列表父页面恢复可见。此方案能直接保留的是画布列表现场；从创作页、项目详情等其他业务页面进入时，那些源页面仍会卸载。若也要恢复它们的组件内状态，必须另外设计其路由保留或逐页状态持久化，`returnTo` 仍只提供导航目标。

路由和动画需要遵循同一个生命周期合同：打开详情时挂载详情并保留列表；若产品要求关闭动画，详情 DOM 必须在退场期间继续存在，动画结束后再销毁。显式点击关闭可以编排这一时序；浏览器后退/前进会先改变历史位置，若也要求一致的退场动画，需要额外的路由过渡或保留退出视图机制，不能假定普通路由卸载会自动等待动画。

**优点**：

- 列表组件不卸载；
- 父页面中的瀑布流已加载页、筛选、滚动位置和临时 UI 状态可随实例保留；
- 符合“从画布列表打开详情，再回来继续浏览”的使用场景。

**缺点**：

- 当前路由和工作台外壳按 `/canvas/:id` 条件卸载侧栏并隐藏顶部栏，需要决定详情打开时哪些外壳继续显示或保持挂载；
- 画布和源页面会同时存在，内存和媒体资源占用更高；
- 路由父子关系需要重构，不能继续把 `/canvas` 和 `/canvas/:id` 当作完全独立的兄弟页面处理；
- 需要处理刷新、直接深链接、新标签页和浏览器后退；
- 需要明确横向轨道或全屏层的 z-index、焦点、键盘和无障碍行为；
- 如果把大型列表整体做 `transform` 左移，需要评估 Safari 和移动端合成层、内存与滚动性能。

适合产品明确要求恢复画布列表现场的情况。若需求是恢复任意来源业务页的完整现场，这个方案本身不够；需要逐页设计状态保留。相比全局保活所有页面，此方案范围更聚焦；相比只记录 `returnTo`，它对画布列表状态的语义更可靠，但实现成本也更高。

### 方案 D：使用浏览器历史后退

使用 `navigate(-1)` 或等价的历史返回。

**优点**：改动最小。

**缺点**：

- 从 `/canvas` 列表进入具体画布时，后退通常只回到 `/canvas`，不一定回到更早的源页面；
- 可能回到外部网站、登录页或其他不适合作为产品返回目标的历史记录；
- 无法定义直接打开画布时的稳定 fallback。

不建议作为完整产品方案，可作为临时行为或辅助按钮。

## 推荐方案

### 产品语义

建议不要让一个叫「主页」的按钮同时承担两个含义：

- 「主页」：固定回 `/`；
- 「返回来源页」：回到进入画布前的业务页面。

如果产品坚持只保留一个按钮，也可以把它改为动态来源返回，但必须在没有来源时回退到固定入口。

### 按来源复杂度分级

| 进入画布的来源 | 推荐策略 | 退出保证 |
| --- | --- | --- |
| `/canvas` 列表卡片或列表内历史抽屉 | 持久列表父页面 + 详情子路由 | 在同一 SPA 页面实例仍保留时，恢复筛选、已加载页、滚动位置及产品决定保留的列表 UI 状态 |
| 创作页、项目详情等其他业务页面 | 校验后的 `returnTo` | 返回进入前的内部页面地址；其他页面内临时状态按其自身实现决定，不作完整现场保证 |
| 画布编辑器内新建画布 | 沿用当前画布会话的原始来源策略 | 不因进入新建的画布而丢失最初的列表/业务页返回目标 |
| 直接访问、刷新后恢复或新标签页打开 | 稳定 fallback（例如 `/canvas`） | 不假设存在可恢复的先前页面实例 |

如果完整保留某个非列表来源页只需很小、局部的改动，可以按同一原则为该来源单独增加保留能力；不应因此默认启用全站页面缓存。

将列表改为持久父页面时，必须清除进入详情时产生的 pending/opening 标记；并明确历史抽屉等入口是否应随返回恢复。当前源码有主动关闭历史抽屉的行为，因此“组件仍挂载”本身不足以证明现场完全恢复。

### 技术路线

推荐先把画布区域改造成一个持久父页面，再在其内部增加详情子路由：

1. 建立 `CanvasRouteLayout` 或等价的画布父级容器。
2. 将画布列表、筛选、分页和滚动容器留在父级，确保进入详情时不卸载；若要保留侧栏实例，还需调整当前工作台外壳按路径卸载侧栏的逻辑。
3. 将具体画布编辑器作为 `/canvas/:id` 详情子路由渲染。
4. 采用横向推入或全屏覆盖的视觉切换；不要用条件渲染直接替换列表组件。
5. 保留明确的“回源页”操作；浏览器后退也应能关闭详情并恢复父页面。若要求浏览器后退时也播放退场动画，需使用能保留退出视图的路由过渡方案。
6. 对直接访问 `/canvas/:id`、刷新和新标签页打开定义明确行为。若详情作为 `/canvas` 的子路由，父级列表会随路由一起匹配；返回控件仍需在缺少有效来源状态时提供 `/canvas` 等稳定 fallback。
7. 统一处理详情打开、详情退场和详情卸载的时序，避免路由变化提前销毁动画或父页面。
8. 从画布列表之外的其他内部业务页面直接进入画布时，额外记录经过校验的来源路由，用于详情关闭后的跨页面返回；只允许应用内路径，并按需筛选查询参数，不能把任意外部 URL 当作返回目标。对这些来源默认只承诺回到原页面地址；只有实现成本低且产品明确需要时，才额外恢复其页面内状态。
9. 明确回源动作与浏览器历史栈的关系：从列表详情打开后，浏览器后退应自然弹出详情并恢复父页面；显式“返回来源页”通常用替换当前详情历史项的方式避免回源后再次回到同一画布，但如果产品需要前进重新打开详情，就必须采用可重入的历史项合同。浏览器后退/前进与显式返回分别验收，避免重复历史项或返回循环。

若核心要求是从 `/canvas` 列表进入详情后恢复该列表的分页、筛选和滚动位置，优先考虑“父页面保持挂载、详情层覆盖或推入”，而不是先把这些状态序列化进 `returnTo`。若要求从任意业务入口返回后也恢复完整现场，则必须逐类评估来源页面的状态模型；单一画布父页面并不能满足该更广的要求。

## 建议验收场景

### 来源 URL

1. 从 `/create` 进入画布，动态回源应恢复 `/create`（以及产品允许保留的查询参数或 hash），而不是一律改写为 `/`；这项保证是回到页面地址，页面内临时状态是否恢复需单独验收。
2. 从短剧项目详情或其画布列表进入画布，分别验证回到原项目详情 tab/view 或画布列表；除非为该来源单独实现并验证了状态恢复，否则不假设源组件实例仍在。
3. 对源码中确认的其他画布列表之外的来源入口逐一验收；如果后续新增从资产页直接打开画布的入口，也要验证回到对应资产页及产品要求保留的状态。
4. 直接访问 `/canvas/:id` 时，返回按钮使用明确 fallback。

### 列表现场

1. 画布列表加载至少 10 页后进入画布，退出后页数不减少。
2. 退出后滚动位置仍接近进入前位置。
3. 搜索词、筛选和排序保持不变。
4. 列表中的选中项、弹窗和抽屉按照产品要求恢复或明确关闭。
5. 刷新页面、打开新标签页、切换账号后不会错误复用旧来源状态。

### 导航安全

1. 来源目标必须限制在当前应用允许的内部路径。
2. 不能把外部 URL、敏感参数或无效画布路径当作返回目标。
3. 删除当前画布、画布加载失败和权限失效时仍有稳定返回路径。
4. 显式回源、浏览器后退/前进和直接深链接不会形成重复历史项或返回循环。
